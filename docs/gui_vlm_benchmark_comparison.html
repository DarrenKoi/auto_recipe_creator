UI Parsing 도구 — 구조화된 요소 검출

UI parsing 도구는 스크린샷을 전처리해 인터랙션 가능한 요소(버튼, 아이콘, 텍스트 필드)를 검출하고, VLM으로 보내기 전에 구조화된 bounding box + label을 제공합니다. 이 과정은 grounding 정확도를 크게 향상시키며, 예를 들어 GPT-4o는 OmniParser 적용 시 0.8%에서 39.6%로 상승합니다.

권장 파이프라인: Parser + GUI 특화 VLM

스크린샷  →  [OmniParser V2 / SparkUI-Parser]  →  구조화 요소 (bboxes + labels + icons)  →  [GUI-Specialized VLM: UI-TARS / MAI-UI / UI-Venus]  →  정밀 Click 좌표 + 액션 계획  →  [pynput Mouse/Keyboard]
왜 결합하나? Parser는 element detection(클릭 가능한 요소의 위치)을 담당하고, GUI-VLM은 semantic grounding(지시문에 맞는 요소 선택)을 담당합니다. 요소가 촘촘한 엔지니어링 UI에서는 이 2단계 접근이 특히 효과적입니다.

OmniParser V2 — 아키텍처 상세

1단계: Detection

  • YOLOv8 Nano를 UI 요소 검출에 맞춰 fine-tuning
  • 버튼, 아이콘, 메뉴, 텍스트 필드, 체크박스 식별
  • 모든 인터랙션 영역의 bounding box 출력
  • V2는 작은 요소(< 20px) 정확도 개선

2단계: Caption + OCR

  • Florence-2 Base를 icon captioning에 맞춰 fine-tuning
  • 각 요소의 기능 설명 생성
  • PaddleOCR로 label/버튼 텍스트 추출
  • 출력: element type, bbox, label, function을 담은 구조화 JSON
OmniTool 연동: Microsoft의 OmniTool은 dockerized Windows 11 VM 환경에서 OmniParser V2와 다양한 VLM(GPT-4o, Claude, Qwen2.5-VL, DeepSeek-R1)을 통합 제공합니다. 또한 local trajectory logging을 지원하여 학습 데이터 파이프라인 구축이 가능하며, RCS/CD-SEM 상호작용 데이터 수집 및 fine-tuning에 직접 활용할 수 있습니다.

RCS 자동화에서 관찰된 Kimi-K2.5 한계

CD-SEM/RCS 엔지니어링 UI 자동화 실험에서 확인된 내용입니다.

좁은 영역(Narrow-Range) 요소 검출 실패

좁은 영역에 UI 요소가 촘촘히 배치되면 Kimi-K2.5는 인접 요소를 안정적으로 구분하지 못하는 경향을 보입니다.

  • 타깃 간격이 < 20px일 때 click 좌표가 인접 요소로 drift
  • 근접 버튼/라벨에서 bounding box가 중첩 출력
  • Toolbar icon 클러스터에서 좌표 출력이 모호해짐
  • 행 높이가 작은 tree-view/list-view를 자주 혼동
  • RCS recipe editor는 요소 간격이 < 10px인 밀집 패널이 다수 존재

근본 원인: GUI Spatial 학습 부재

Kimi-K2.5 같은 범용 VLM은 자연 이미지, 문서, 웹 스크린샷 중심으로 학습되어 밀집 엔지니어링 UI에 최적화되어 있지 않습니다. 다음 능력이 부족합니다:

  • 작은 타깃에 필요한 sub-pixel 좌표 정밀도
  • 요소 경계 인식을 위한 GUI 특화 spatial encoding
  • widget type 인지 (legacy UI에서는 버튼/라벨/input 외형이 유사)
  • 전문 디스플레이(1920x1080+) 대응 고해상도 patch 처리
  • ScreenSpot-Pro에서도 타깃 box 면적이 작아질수록 정확도가 급격히 하락, 범용 모델의 icon-only grounding은 < 5% 수준
해결책: Parser + GUI-VLM 파이프라인. OmniParser 같은 UI parser가 인터랙션 요소를 정밀 bounding box로 먼저 검출하고, 이후 GUI 특화 VLM이 지시문과 정답 요소를 매칭합니다. 즉 요소가 어디 있는지(parser)와 어떤 요소를 클릭할지(VLM)를 분리해 narrow-range 검출 실패를 직접적으로 완화합니다.

UI Parsing / 전처리 도구

OmniParser V2 Parser

Microsoft Research — 오픈소스 (MIT)
YOLOv8(detection) + Florence-2(icon caption) + PaddleOCR 구성. 임의 스크린샷을 bounding box 기반 구조화 요소로 변환하며, ScreenSpot-Pro에서 GPT-4o를 0.8%에서 39.6%로 향상시킵니다. V1 대비 60% 빠르며 OmniTool이 agent 테스트용 dockerized Windows VM을 제공합니다.
Latency: 0.6s/frame (A100) VRAM: ~4-8GB

SparkUI-Parser Parser

Ant Group — 오픈소스
연속 좌표 모델링(비이산)을 사용하는 end-to-end 프레임워크. MLLM backbone + token router + coordinate decoder 구조이며, 작은 요소 정밀도와 parser 추론 속도 측면에서 강점을 보입니다.
Approach: Continuous coord regression

Set-of-Mark (SoM) Prompting

Microsoft Research — 오픈소스
검출된 UI 요소 위에 번호 마크를 입히는 visual prompting 기법입니다. VLM이 raw 좌표 대신 번호 기반으로 요소를 참조할 수 있어 안정성이 높아지며, 어떤 detection 모델과도 결합 가능합니다.
Type: Visual prompt overlay VRAM: 거의 없음 (overlay만 수행)

핵심 결론

문제: Kimi-K2.5 한계

  • ScreenSpot-Pro 52.8% — GUI 최적화가 아닌 범용 모델
  • 좁고 밀집된 UI 영역에서 요소 구분 안정성이 낮음
  • 전문 엔지니어링 UI에서 icon/widget 검출 성능이 약함
  • 우리 RCS/CD-SEM 인터페이스에 맞춘 fine-tuning이 어려움
  • 현재 파이프라인에 UI parsing 전처리가 없음

해결: Parser + GUI 특화 VLM

  • UI-Venus-1.5-8B 기준 69.6% — Kimi-K2.5 대비 +32% 향상
  • OmniParser가 정밀 bbox로 요소를 선검출해 narrow-range 이슈 완화
  • 오픈소스 기반 독립 GPU self-hosted 가능 — 기존 Kimi 서비스와 분리 운영
  • 사내 RCS/CD-SEM 스크린샷으로 fine-tuning 가능
  • OmniTool trajectory logging으로 학습 데이터 수집 가능
