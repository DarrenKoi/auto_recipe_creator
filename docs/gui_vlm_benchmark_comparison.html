UI Parsing Tools — Structured Element Detection

UI parsing tools pre-process screenshots to detect interactive elements (buttons, icons, text fields) and provide structured bounding boxes + labels before sending to a VLM. This dramatically improves grounding accuracy — e.g., GPT-4o jumps from 0.8% to 39.6% with OmniParser.

Proposed Pipeline: Parser + GUI-Specialized VLM

Screenshot  →  [OmniParser V2 / SparkUI-Parser]  →  Structured Elements (bboxes + labels + icons)  →  [GUI-Specialized VLM: UI-TARS / MAI-UI / UI-Venus]  →  Precise Click Coordinates + Action Plan  →  [pynput Mouse/Keyboard]
Why combine? The parser handles element detection (where are the clickable things?) while the GUI-VLM handles semantic grounding (which element matches the instruction?). This two-stage approach is especially powerful for dense engineering UIs where elements are tightly packed.

OmniParser V2 — Architecture Detail

Stage 1: Detection

  • YOLOv8 Nano fine-tuned for UI element detection
  • Identifies buttons, icons, menus, text fields, checkboxes
  • Outputs bounding boxes for all interactive regions
  • V2 improves accuracy on small elements (< 20px)

Stage 2: Caption + OCR

  • Florence-2 Base fine-tuned for icon captioning
  • Generates functional descriptions for each element
  • PaddleOCR extracts text from labels and buttons
  • Output: structured JSON with element type, bbox, label, function
Integration with OmniTool: Microsoft's OmniTool provides a dockerized Windows 11 VM that integrates OmniParser V2 with various VLMs (GPT-4o, Claude, Qwen2.5-VL, DeepSeek-R1). It also supports local trajectory logging for building training data pipelines — directly useful for collecting RCS/CD-SEM interaction data for fine-tuning.

Observed Kimi-K2.5 Limitations in RCS Automation

Based on real-world testing with CD-SEM/RCS engineering UI automation.

Narrow-Range Element Detection Failure

When multiple UI elements are packed closely together in a narrow region, Kimi-K2.5 cannot reliably distinguish adjacent elements.

  • Click coordinates drift to neighboring elements when targets are < 20px apart
  • Overlapping bounding boxes for closely-spaced buttons/labels
  • Toolbar icon clusters produce ambiguous coordinate outputs
  • Tree-view and list-view rows with small row-height are frequently confused
  • RCS recipe editor has dense control panels with < 10px element spacing

Root Cause: No GUI Spatial Training

General-purpose VLMs like Kimi-K2.5 are trained on natural images, documents, and web screenshots — not dense engineering UIs. They lack:

  • Sub-pixel coordinate precision required for small targets
  • GUI-specific spatial encoding for element boundary detection
  • Widget-type awareness (buttons vs labels vs inputs look similar in legacy UIs)
  • High-resolution patch processing for professional displays (1920x1080+)
  • ScreenSpot-Pro confirms: accuracy degrades rapidly as target box area decreases, and icon-only grounding drops to < 5% for general models
Solution: Parser + GUI-VLM Pipeline. A UI parser like OmniParser pre-detects all interactive elements with precise bounding boxes, then a GUI-specialized VLM matches the instruction to the correct element. This two-stage approach specifically addresses the narrow-range detection failure by separating where are the elements (parser) from which element to click (VLM).

UI Parsing / Pre-Processing Tools

OmniParser V2 Parser

Microsoft Research — Open Source (MIT)
YOLOv8 (detection) + Florence-2 (icon caption) + PaddleOCR. Converts any screenshot into structured elements with bounding boxes. Boosts GPT-4o from 0.8% to 39.6% on ScreenSpot-Pro. 60% faster than V1. OmniTool provides dockerized Windows VM for agent testing.
Latency: 0.6s/frame (A100) VRAM: ~4-8GB

SparkUI-Parser Parser

Ant Group — Open Source
End-to-end framework with continuous coordinate modeling (not discrete). MLLM backbone + token router + coordinate decoder. Highest precision for small elements and fastest inference speed among parsers.
Approach: Continuous coord regression

Set-of-Mark (SoM) Prompting

Microsoft Research — Open Source
Visual prompting technique that overlays numbered marks on detected UI elements. VLM then references elements by number instead of raw coordinates. Can be combined with any detection model.
Type: Visual prompt overlay VRAM: Negligible (overlay only)

Key Takeaways

Problem: Kimi-K2.5 Limitations

  • 52.8% on ScreenSpot-Pro — general-purpose model not optimized for GUI
  • Cannot reliably distinguish elements in narrow/dense UI regions
  • Icon/widget detection weak on professional engineering UIs
  • Not fine-tunable for our specific RCS/CD-SEM interface
  • No UI parsing pre-processing in current pipeline

Solution: Parser + GUI-Specialized VLM

  • 69.6% accuracy (UI-Venus-1.5-8B) — +32% improvement over Kimi-K2.5
  • OmniParser pre-detects elements with precise bboxes — solves narrow-range issue
  • Open-source, self-hosted on dedicated GPU — no impact on existing Kimi service
  • Fine-tunable on proprietary RCS/CD-SEM screenshots
  • OmniTool provides trajectory logging for training data collection
