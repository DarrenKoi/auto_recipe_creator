## 0. 이 세션의 한 줄 요약

오피스에서 registration verifier A/B 를 3차례 돌려 그 결과(digest)를 릴레이받아가며,
**여러 검증기(verifier arm) 중 살아남는 것만 골라내고 → 검증된 것 하나(MIND)만 실제
production(workflow_3)에 이식**했다. 그리고 "무엇을 더 개선할 수 있고 무엇은 원리상
개선 불가인지"를 데이터로 보여주는 **커버리지 집계**를 벤치에 추가했다.

이 저널은 특히 마지막에 추가한 **pm(proposer_miss) / re(rank_error)** 개념을 자세히
설명한다 — 이게 "앞으로 어디에 노력을 쏟아야 하는가"를 결정하는 핵심 지표이기 때문이다.

## 1. 배경 지식 — 이 실험이 푸는 문제

### 1.1 매칭 파이프라인은 2단이다

align fail(장비의 정렬 실패) 이 나면, 등록된 "정렬 키(align key)" 이미지를 현재 SEM
화면 어디에 있는지 찾아야 한다. 이걸 두 단계로 푼다:

1. **proposer(후보 제안기)** — 화면 전체를 훑어 "정렬 키일 것 같은 위치" 후보 8개를 낸다.
   (3채널 구조 매칭 ensemble; 이미 production 에 있음)
2. **selection(선택기)** — 후보 8개 중 진짜 1개를 고른다.

### 1.2 실패는 세 종류로 나뉜다 (이번 세션의 핵심 프레임)

정답(GT, ground truth)이 후보 목록에서 몇 등인지로 실패를 분류한다:

| 분류 | 뜻 | 고칠 수 있나 |
|---|---|---|
| **rank1_ok** | 정답이 이미 1등 | 고칠 것 없음 (이미 성공) |
| **rank_error** | 정답이 후보엔 있는데 1등이 아님 | **selection 을 고치면 회복 가능** |
| **proposer_miss** | 정답이 후보 8개에 아예 없음 | selection 으로는 **불가능** |

이 표가 이번 세션 전체를 관통하는 프레임이다. **"검증기(verifier)"라는 도구는
rank_error 만 고칠 수 있다** — 후보들의 순서를 다시 매기는 도구라서, 목록에 없는 답
(proposer_miss)은 손댈 수 없다. 그래서 rank_error 버킷 크기가 검증기가 낼 수 있는
개선의 이론적 상한이다.

### 1.3 verifier(검증기) 란

proposer 가 낸 후보 각각을 다시 뜯어보고 "이게 진짜 정렬 키가 맞나"를 재채점해서
순위를 바로잡는 2차 심판. 이번에 실험한 arm(검증기 후보)들:

- **ecc** — 밝기 기반 국소 정합 (findTransformECC)
- **phase / phase_ecc** — 푸리에 위상차로 이동량 추정 (+ ecc 로 정밀화)
- **grad_phase** — 밝기 대신 경사(gradient) 위에서 phase
- **sift / akaze** — 특징점 매칭 (keypoint + RANSAC)
- **mind** — 자기유사성(self-similarity) 기반 재채점 ← **최종 생존자**
- **fuse** — 여러 arm 의 순위를 RRF 로 합의 (의사-arm)

## 2. 진행 사항 (시간 순)

### 2.1 1차 실측 판독 → 생존자 선별

오전에 확장한 7종 arm 을 오피스 golden(40 recipe, 195점)에서 처음 돌린 결과를 받아
판독했다:

- **mind 만 유망** (+0.031, 살린 점/망친 점 = 10/4)
- ecc / grad_phase = churn (살리는 만큼 망침, 동전던지기)
- **phase / phase_ecc = 유해** (regress 가 promote 의 2배 — phase 의 오추정이
  cascade 로 전파됨. 과거 POC-rerank 우위가 verifier 국면에선 재현 안 됨)
- **sift / akaze = 전 후보 거부** (0/0, 전부 baseline 폴백. SEM 저텍스처/aperture 와
  정합 — 특징점 기반은 이 도메인에 부적격)

→ 기본값을 생존자만으로: `ARMS=ecc,mind`, 전체 recipe(sample_n=0). (`1c44d78`)

### 2.2 digest 에 modality 델타 추가

digest 한 줄만 릴레이받는 워크플로우에서 "SEM/OM 어느 쪽 이득인지"를 표 없이 읽도록
각 arm 에 `[om±/sem±]` 부가. (`3fb7f58`)

### 2.3 2차 실측 → **판정 관문 발견 (prod/prod_mind)**

전체 67 recipe(334점)로 재실행:

- mind +0.039 (om +0.035, sem +0.041) — **문제 축인 SEM 에서 더 큰 이득**, 부호검정 p≈2%
- **fuse(ecc,mind) = 정확히 ±0** — ecc 잡음이 RRF 에서 mind 신호를 상쇄 → **fuse 기각**
- err_med 0.0>0.5 = golden GT 가 정수 격자라 **sub-pixel 축은 측정 불가**,
  이득은 전부 순위 교정에서 나옴 → 포팅 형태는 rerank 전용

그런데 **중요한 간극**을 발견했다: 벤치의 baseline(B0)은 RRF proposer 순서인데,
**실제 production 은 이미 그 위에 NCC rerank(sel = 0.5·chamfer + 0.5·NCC)를 얹어**
최종 후보를 고른다. 즉 mind 의 "+0.039"가 운영의 NCC 가 이미 잡는 오류와 겹칠 수 있다.
겹치면 포팅 이득은 0, 직교면 결합이 더 오른다 — 미측정 상태로는 포팅 불가.

→ 드라이버에 판정용 의사-arm 2개 추가 (`a521537`):
- **prod** = 운영 NCC selection 을 bit-단위 재현 (engine 함수 그대로 import)
- **prod_mind** = prod 순서 + mind 순서의 RRF 결합 = 포팅 후보안
- 판정식: **prod_mind > prod 여야 mind 포팅 가치 있음**

### 2.4 3차 실측 → **판정 통과, 포팅 실행**

```
prod      r1=0.784 d=+0.009 [om-0.014/sem+0.026] p/r=22/19  ← 운영 NCC 단독(거의 중립)
prod_mind r1=0.817 d=+0.042 [om+0.021/sem+0.057] p/r=26/12  ← 결합(포팅안)
```

**prod_mind(0.817) > prod(0.784) → mind 는 NCC 와 직교 확정.** SEM 에서 +0.026→+0.057 로
두 배 이상. → workflow_3 engine 에 포팅 (`f38582d`):

- `poc/workflow_3/align/matching/mind_rerank.py` 신규 (registration_lab bit-parity)
- `compute_align_key_score_ensemble` 의 selection 을 "sel 순서 ⊕ mind 순서 RRF 결합"으로
- score-only(좌표는 기존 후보 중 하나), 전 후보 거부 시 NCC selection 폴백,
  킬스위치 `ALIGN_FAIL_MIND_RERANK=0`
- smoke 5/5 + 회귀(engine 10/10, ensemble+driver 26, correction 13/13)

## 4. pm / re 개념 상세 — "무엇을 더 개선할 수 있는가"

이 세션 마지막에 추가한 커버리지 집계는 다음 질문에 답한다:
**"아무 알고리즘도 정답에 도달 못한 케이스는 정말 개선 불가인가?"**

답은 **"절반만 그렇다"** 이고, 그 절반을 가르는 게 pm 과 re 다.

### 4.1 oracle — 도달 가능 상한

먼저 각 점에서 **B0(proposer 1등)와 모든 arm(mind/prod/prod_mind/…)을 통틀어
하나라도 정답을 맞췄는가**를 본다. 하나라도 맞췄으면 `oracle_hit`. 이건 "지금 가진
방법들을 전부 동원했을 때의 이론적 최대 성적"이다. prod_mind 단독(0.817)보다 조금
높을 수 있는데, prod_mind 가 놓쳤지만 다른 arm 이 잡은 점이 있기 때문이다.

### 4.2 all_miss — 아무도 못 잡은 점, 그리고 두 갈래

`oracle_hit` 이 아닌 점 = 어떤 방법으로도 GT 도달 실패. 이걸 bucket 으로 나눈다:

**pm (proposer_miss) — 후보에 GT 자체가 없다**

- 정답이 proposer 가 낸 후보 8개 안에 애초에 없다.
- verifier/rerank 는 "있는 후보의 순서를 다시 매기는" 도구다. 목록에 없는 답을 위로
  끌어올릴 수단이 **원리적으로 없다.** mind 든 NCC 든 어떤 조합도 여기선 무력하다.
- **→ 이건 rerank 축에서는 개선 불가가 맞다.** 하지만 "영원히 불가"가 아니라
  **레버가 다른 축**이라는 뜻이다:
  - **재등록** — proposer 가 후보로도 못 잡는다는 건, 그 정렬 키가 화면에서 충분히
    독특하지 않다는 신호다. 더 변별력 있는 위치로 align key 를 재등록하는 게 정답.
    (이건 기존 결론 [[project_reregister_report_phase1]] 이 정확히 겨냥하던 것)
  - proposer 자체 개선(후보 수 top_n↑, 새 채널) 또는 VLM-region escalation

**re (rank_error) — GT 는 후보에 있는데 전 arm 이 실패**

- 정답이 후보 안에 **있는데도** 현재 검증기 조합(NCC + mind)이 1등으로 못 만들었다.
- **→ 이건 "현재 방법으로 미해결"이지 "개선 불가"가 아니다.** 아직 안 써본 다른
  표상의 verifier, template-bank 등이 남은 여지다.
- **re 숫자가 곧 "다음 verifier 실험에 걸린 판돈"** 이다. re 가 크면 새 검증기를 더
  파볼 가치가 있고, re 가 작으면 남은 개선은 거의 전부 재등록 축(pm)으로 넘어간다.

**rank1_ok** — 정의상 B0 가 이미 GT 라서 커버리지 miss 가 0 이다(방어적으로만 집계).

### 4.3 왜 이 분해가 중요한가

이 표가 없으면 "정렬이 아직 18% 틀린다"는 뭉뚱그린 숫자만 남는다. 분해하면:

- **pm 몫** → CV 알고리즘을 아무리 개선해도 못 줄인다. 엔지니어의 **재등록 작업**이
  유일한 레버. "이 recipe 들은 재등록 대상"이라는 실행 가능한 결론이 된다.
- **re 몫** → CV 쪽에서 더 짜낼 수 있는 몫. 다음 verifier 실험의 기대 상한.

즉 **노력을 CV(코드)에 쓸지 재등록(운영)에 쓸지를 데이터가 직접 지시**한다.

### 4.4 구현 요약

```
# golden_registration_eval_cond.py, 점마다:
any_arm_hit = any(e["hit_ref"] for e in row["arms"].values())
oracle_hit  = b0_hit or any_arm_hit
if not oracle_hit:
    coverage[mod][f"miss_{bucket}"] += 1   # pm 또는 re 로 자동 분류
```

불변식 **`oracle_hit + all_miss == n`** 을 테스트로 고정(집계에 구멍 나면 깨짐).
출력: 표(mod별+통합) + digest `oracle=.. allmiss[pm=../re=..]` + summary.coverage.

디지스트 예시(합성 렌더): `oracle=0.878 allmiss[pm=29/re=7]` — 실패 36점 중 29점은
재등록으로만, 7점만 verifier 로 더 짜낼 여지.
