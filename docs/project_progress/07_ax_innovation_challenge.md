## 1. 사례 요약

### 한 줄 요약

R3 연구소 팹 CD-SEM(반도체 미세 패턴의 치수를 측정하는 전자현미경 계측 장비) 26대의 Wafer In-line
측정 시 Align Fail(정렬 실패)이 **주 400~500건** 발생합니다. 현업 담당자가 알람을 보고 원격 접속해
**1건 5분**씩 수동으로 고치던 일을 **AI Agent가 감지·접속·재정렬·기록까지 무인으로 수행하고
되돌릴 수 없는 최종 확정(OK)만 현업 담당자가 누르는 반자동 방식**으로 바꾼 사례입니다. 감지에서 위치
재조정까지 걸리는 시간은 **1분 미만**으로 줄었습니다(2026-08 실장비 반자동 운영 시작, 2026-09 개인 PC에서
실알람 대응과 현업 합동 시험 수행, 전용 PC를 확보해 R3 26대 실전 배치 준비 중).

### Story 1 — 문제: 5분짜리 반복 작업이 장비를 세우고 있었다

계측 장비는 Wafer를 측정하기 전에 Recipe(장비 측정 설정)에 등록된 기준 이미지(Align Key)를 실제 Wafer 화면에서 찾아 좌표를 맞춥니다. 공정 변동으로 등록 이미지와 실제 화면이 조금씩 달라지면 장비는 정렬에 실패하고 **그 자리에서 멈춥니다**. Split Lot(공정 조건을 나눠 시험하는 실험 로트)이 많은 연구소 팹에서는 이 실패가 전체 측정의 약 5%, 주 400~500건에 이릅니다.

멈춘 장비를 다시 움직이는 절차는 정형화되어 있지만 전부 현업 담당자 손을 탑니다. 알람을 눈으로 확인한 뒤 RCS(Remote Control System, 장비 원격 제어 프로그램)를 실행해 로그인합니다. 장비 목록에서 해당 장비를 찾아 접속하고, 멈춘 화면에서 Align Key 위치를 배율을 바꿔가며 육안으로 찾아 재조정한 뒤 확정을 누릅니다. 알람 인지에서 위치 재조정까지 1건당 평균 5분, 그 5분은 전부 장비 idle입니다. 주 400건 기준으로도 **주 약 33시간**의 계측 장비 시간이 현업 담당자의 반응 속도에 묶여 있었습니다. 이 대응에 Fab 인라인 구성원과 현업 엔지니어가 24시간 교대로 알람을 지켜봐야 했습니다. 야간·교대 인계 구간에서는 확인이 늦어지기 쉬웠습니다. 실패 시점의 화면도 남지 않아 어떤 Recipe가 만성적으로 실패하는지 화면 근거로 분석할 수 없었습니다.

이 일을 그동안 자동화하지 못한 데는 이유가 두 가지 있었습니다.

1. 계측 클라이언트 화면이 표준 UI 컴포넌트로 만들어져 있지 않아 **일반 RPA·UI 자동화 도구가
   버튼을 인식하지 못합니다.**
2. Align Key는 매번 조금씩 다르게 찍히므로 **고정 좌표·고정 템플릿 스크립트로는 풀리지 않습니다.**

즉 화면의 의미를 이해하는 능력과 픽셀 단위 정밀도가 동시에 필요한 일이라 규칙 기반
자동화의 사각지대였습니다.

### Story 2 — 해결: 하나의 AI에 다 맡기지 않고, 이해·확인·정량·확정을 나눴다

두 벽을 넘은 열쇠는 AI와 CV(Computer Vision, 영상 비교·좌표 계산 기술)의 역할 분리입니다. 처음에는 화면을 보고 조작하는 VLM(Vision
Language Model, 화면을 이해하는 AI) 하나에 클릭까지 맡겨 봤지만 좌표가 어긋나고 반복할수록
오류가 늘었습니다. 그래서 판단을 네 주체에 나누고 뒤 단계가 앞 단계의 답을 검증하도록
연결했습니다.

| 주체 | 맡은 질문 | 하는 일 |
|------|-----------|---------|
| **VLM** (사내 HCP, 즉 사내 모델 운영 플랫폼에 자체 배포한 소형 모델) | "어디를 볼지" | 화면에서 UI 요소 위치를 찾습니다(전체에서 대략 → 잘라 확대해 정밀, coarse → fine 2단계). 라이브 SEM 화면 영역을 검출하고 촬영 모드(저배율 OM / 고배율 SEM)도 판독합니다 |
| **OCR 모델** (PaddleOCR-VL, 화면 문자를 읽는 AI. VLM과 같이 사내 HCP에 자체 배포) | "정말 그 버튼이 맞는지" | VLM이 찍은 지점의 라벨을 읽어 의도한 대상인지 대조합니다. 다른 장비 ID가 읽히거나 확인이 안 되면 **클릭하지 않습니다**(fail-closed) |
| **CV 매칭 엔진** (영상 비교로 위치를 계산) | "정확히 몇 픽셀인지" | 기준 이미지와 라이브 화면의 유사도 점수와 최종 재정렬 좌표를 산출합니다. 기준 이미지는 최근 정렬 성공 사례 여러 장을 종합(consensus)한 것을 우선 쓰고, 성공 사례가 부족하거나 저품질이면 등록 이미지 1장으로 되돌아갑니다 |
| **현업 담당자** | "되돌릴 수 없는 것" | 재정렬 결과를 보고 확정(OK)을 누르고 모드 불명·위치 모호·타인 점유 같은 예외를 처리합니다 |

여기에 세 가지 원칙을 코드에 고정했습니다. VLM의 답이 낮은 CV 점수를 덮어쓰지 못합니다.
검증 대상 클릭은 확인에 실패하면 나가지 않습니다. 되돌릴 수 없는 조작은 현업 담당자가 합니다. 화면 이해와 문자
확인은 소형 AI 모델 2종(VLM·OCR)이 맡고 반복되는 정밀 판정은 CV가 맡습니다. 그 덕분에 거대 모델 없이 GPU 1~2장 규모의 소형
오픈소스 모델(외부 API 의존 없음)로 26대를 모니터링하도록 설계했습니다.

![그림 2. AI 역할 분리](img/07/fig2_role_split.png)

그 결과 **알람 감지(10초 폴링) → 담당자 사전 고지 → RCS 자동 접속 → 상시 녹화 → 화면·촬영 모드
판독 → 성공 사례 기반 자동 재정렬 → 확정 요청 알림 → (현업 담당자 OK) → 완료 감시·자동 종료 → 대응
기록 1줄 적재**가 한 루프로 돕니다. 정상 경로에서 현업 담당자가 맡는 단계는 확정(OK) 하나입니다. 보정이
불가능하거나 다른 엔지니어가 장비를 쓰고 있으면 원인과 요구 행동을 담아 알리고 물러납니다. 처리 중
예외가 나도 녹화 종료·창 닫기·팝업 정리를 순서대로 시도합니다.

정확도는 실장비를 건드리지 않는 오프라인 벤치(Recipe 200개)에서 A/B로 확보했습니다. 시도한
개선안 중 데이터로 이긴 2가지(성공 사례 종합, 촬영 모드에 맞춰 후보 순서를 다시 매기는 재순위)만
운영 시스템에 반영하고 효과가 없거나 작은 대안은 제외했습니다. 재순위 후 남은 실패의 약 87%는
정답이 후보 목록에 아예 없는 유형임을 확인했습니다. 순위 조정만으로는 풀리지 않는 몫이라,
Align Key를 더 구별되는 위치로 재등록하는 과제로 현업과 함께 검토하기로 했습니다.

### 이 사례의 의미 — 세 줄

1. **기존 UI 요소 인식 방식으로는 자동화가 어려웠던 대상**(비표준 UI + 매번 달라지는 정답)을

3. **기술로 풀 것과 현업 담당자가 풀 것을 데이터로 갈랐습니다.** 개선안은 벤치로 채택·기각했습니다.
   순위 조정으로 풀리지 않는 잔여 실패는 Align Key 재등록이라는 현업 협업 과제로 정의했습니다.

## 2. 사례 상세

### 2.1 해결하려는 업무 문제와 현업 필요성

**대상 업무.** R3 연구소 팹 CD-SEM 계측 장비 26대(설치 28대 중 2대는 fab-out)의 Align Fail(Smart Alarm 코드 9006) 대응입니다.
계측 장비는 측정 전에 Recipe에 등록된 Align 이미지를 Wafer 화면에서 찾아 좌표를 맞춥니다. 이 정렬이 실패하면 장비는 **진행을 중단하고 현업 담당자가 조치할 때까지 홀드**됩니다.

**왜 반복되는가.** R3는 연구소 팹이라 공정 Lot Split과 공정 Variation이 많습니다. 그래서 Recipe에 등록된 이미지와 실제 Wafer에서 찍힌 Align 이미지가 달라지는 일이 구조적으로 되풀이됩니다. Align Fail은 **CD-SEM 전체 측정 건수의 약 5%, 주 400~500건** 규모로 반복 발생합니다. 한두 번 고쳐서 없어지는 문제가 아닙니다. 실험 조건이 다양해서 계속 되풀이됩니다. 이하 효과 환산은 보수적으로 하한 400건을 씁니다.

**현업 필요성.**

- **장비 홀드가 계측 대기 물량을 쌓는다.** Align Fail 1건은 그 장비의 측정을 멈추고 뒤에 선 Lot 전체를 기다리게 합니다. 계측 WIP이 밀리면 공정 결과 확인과 후속 실험 일정, 곧 연구소 팹의 **개발 속도**가 지연될 수 있습니다.
- **24시간 대응 체계에 현업 담당자가 묶여 있다.** Fab 인라인 구성원과 현업(MI) 엔지니어가 알람을 확인하고 조치하는 일을 24시간 나눠 맡고 있습니다. 절차는 정형화되어 있지만 화면을 보고 판단하는 단계가 있어 숙련자의 판단이 필요합니다. 그 시간이 반복 작업에 들어갑니다.
- **기록이 없다.** 알람 이력으로 빈도는 알 수 있어도 실패 시점의 화면이 남지 않아 어떤 Recipe의 Align Key가 왜 실패하는지, 재등록이 필요한지 화면 근거로 판단하기 어려웠습니다.

### 2.2 기존 방식의 비효율·반복·편차·장애 요인

| 단계 | 기존 수행 방식 | 비효율·편차·장애 요인 |
|------|----------------|-----------------------|
| 감지 | Fab 인라인·엔지니어가 알람 화면을 눈으로 확인 | 현업 담당자의 확인 주기에 의존. 야간·주말·교대 인계 구간에 지연 |
| 접속 | RCS 실행·로그인·장비 목록 탐색·접속 | 매 건 같은 조작 반복. 장비 클라이언트가 비표준 UI라 기존 UI 요소 인식 방식으로 자동화하기 어려움 |
| 판단 | 멈춘 화면에서 Align Key 육안 탐색(배율 변경 포함) | 숙련도 편차. 비슷한 패턴이 반복되는 고배율 화면은 현업 담당자도 오판 |
| 보정 | 화면 재조정 후 확정 | 위치 정밀도가 개인의 손에 좌우 |
| 기록 | 없음 | 원인·재발 Recipe 축적 불가, 개선 우선순위를 감으로 결정 |

1건당 평균 5분, 그 5분은 전부 장비 idle입니다. 주 400건 기준 **주 약 33시간**의 계측 장비 시간이
현업 담당자의 반응 속도에 묶여 있었습니다(500건이면 약 42시간).

### 2.3 AI 적용을 위해 거친 주요 과정과 새로운 시도

프로젝트는 2026년 2월 요구사항 정의와 화면 이해 AI 확보에서 시작해 4단계로 진행했습니다.

**① 화면 이해 AI 확보: 오픈웨이트 모델 비교 → 1종 선정 (설치·초기 비교 2026-02~03, 운영 구성 확정 2026-08)**

외부 API에 기대지 않고 Hugging Face의 오픈웨이트(가중치 공개) 최신 모델 여러 종을 사내 HCP(Hybrid Cloud
Platform)에 직접 설치해 비교했습니다. 화면 이해 VLM 3종(MAI-UI, UI-Venus, UI-TARS)과 OCR
2종(PaddleOCR-VL, GOT-OCR)입니다. Flask 통합 API 한 곳으로 라우팅해 모델을 바꿔 끼울 수 있게 했습니다.

평가 대상 화면은 일반 UI/UX와 다릅니다. 장비 제조사(BP사)가 소수의 엔지니어를 위해 만든 도구라
버튼이 오밀조밀 모여 있고 기능이 많아 현업 담당자도 조작이 어렵습니다. 실제 업무 화면으로 반복 측정한
결과 MAI-UI가 성공률이 가장 높았습니다(장비 화면 좌표 인식과 클릭까지 포함한 500회 반복 시험 99%
성공, 현업 집계) `[검증]`. §3의 버튼 판독 100%는 이와 별도의 클릭 미실행 벤치입니다. MAI-UI는 스마트폰 화면
자동화용으로 튜닝된 소형 모델입니다. 작은 버튼이 빽빽한 모바일 화면용 모델이 엔지니어링 도구 화면에도
적용 가능함을 확인한 점이 특이했습니다. 반복 평가를 거쳐 2026-08에 화면 좌표 인식을 MAI-UI로 통일하고
AI 모델 2종(VLM 1종 + OCR 1종) 상시 운영으로 정리했습니다. 모델 교체는 벤치 결과로 결정하는 체계를 갖췄습니다.

**② 장비 원격 제어(RCS) 자동화 증명 (2026-03~05, workflow_1)**

장비를 컨트롤하려면 원격 제어 프로그램 RCS부터 자동으로 다뤄야 했습니다. 처음엔 GUI 조작형 모델 하나에
클릭까지 맡겼습니다. 한 번에 좌표를 찍는 방식은 확률적으로 실패율이 높았고 반복할수록 오류가
쌓였습니다. 그래서 판단을 2단계로 나눴습니다. 전체 화면에서 대략 영역을 찾고(coarse), 그 영역만 잘라
확대해 정밀 클릭점을 정하고(fine), 클릭 전 그 자리의 라벨을 OCR로 읽어 확인(confirm)합니다.

고정 좌표·고정 이미지를 지정하는 기존 방식(pyautogui 류) 대신 프롬프트로 목표를 설명하면 VLM이
화면에서 위치를 찾는 방식을 택했습니다. 그래서 "어떤 말로 물어야 정확히 찍는가"가 성능을 좌우했습니다.
표현을 바꿔 반복 시험하며 인식 안정성을 높였습니다(첫 글자를 먼저 찾게 하는 anchoring 등). 이 방식으로
로그인·탭 이동·장비 선택·화면 캡처·창 닫기를 오피스 실장비에서 안정적으로 수행함을 확인했습니다.

**③ 정렬 정확도 확보: 오프라인 A/B 벤치 (2026-05~07, workflow_2)**

Recipe 200개의 등록 이미지와 과거 Align Fail 이미지를 내려받아 실장비를 건드리지 않는 평가 환경을
만들었습니다. 정답 좌표는 등록 당시 조건 정보로 산출했고 사람 라벨은 쓰지 않았습니다. 성공 이미지로
기준을 만들 때는 평가 대상을 빼는 교차검증을 적용했습니다. 여기서 검증된 방식만 운영 루프에 반영한다는
규율을 지켰습니다. 채택한 것은 2가지입니다. 성공 이미지 여러 장을 종합한 기준을 쓰자 정답을 첫 후보로 고르는 비율이 31.8%에서
76.4%로 올라갔습니다. 별도 평가에서는 촬영 모드별 후보 재평가 방식을 채택했습니다. 관심 영역 축소,
개별 보관 방식, 윤곽선 채널, 이중 종합, 십자선 제거 등 효과가 없거나 작은 대안은 데이터로 제외했습니다.

**④ 실시간 통합 루프 (2026-06~, workflow_3)**

알람을 실시간으로 받는 기반 작업이 먼저 필요했습니다. R3 Align Fail 알람을 사내 data-hub에
적재했습니다. 사내 알람 연계 서비스 h-api를 시스템이 **10초 간격**으로 조회해 알람 내용을 받도록
연결했습니다. 그 위에 ①~③을 묶어 알람 감지부터 기록까지 무인으로 도는 루프를 구축했습니다. 2026-08에는
실장비 반자동 보정을 운영에 적용하기 시작했습니다. 8~9월에는 실행과 기록·판정을 분리해 실패 회복 과정을 기록하는
계층(Recovery Episode)을 더했습니다.

**새로운 시도 3가지**

1. **성공 사례 종합(consensus) 기준 이미지**: 처음 등록한 이미지 1장을 계속 쓰지 않고 최근 정렬
   성공 이미지 여러 장을 위치 맞춰 합성해 지금의 Wafer 외관을 따라가는 기준을 만들었습니다.
   이것 하나로 1순위 적중률이 2배 이상 올랐습니다. 같은 Recipe면 장비가 달라도 성공 이력을 공유합니다.
2. **촬영 모드별 후보 평가 방식 전환**: 저배율(OM)과 고배율(SEM)에서 서로 다른 재순위 심판이 이긴다는 것을
   A/B로 발견했습니다. 처음엔 심판들을 투표로 섞었는데 성적이 떨어졌습니다. 한 심판이 특정 국면을
   지배할 때는 종합보다 전환이 옳다는 것을 데이터로 확인하고 구성을 바꿨습니다.
3. **암묵지 자산화 경로**: 알람이 없어도 엔지니어의 수동 조작을 화면만 관측해 녹화합니다. 이 기록을
   조작 타임라인 → 한국어 절차서로 바꾸는 경로를 만들었습니다. 입력 후킹은 하지 않고 화면만 보도록
   동의 범위를 코드에 고정했습니다.

**녹화의 목적과 목표**

루프는 접속 즉시 장비 화면을 상시 녹화합니다. 알람이 없을 때도 엔지니어가 동의하면 수동 조작 세션을
녹화합니다. 목적은 넷입니다.

| 목적 | 무엇을 남기나 | 사용자·활용처 |
|------|---------------|-----------|
| **증거** | 실패 시점 화면과 대응 전 구간(AI 동작 + 엔지니어 개입) | 보정 실패·오동작 원인 분석, AI가 무엇을 눌렀는지 사후 감사 |
| **재등록 판단** | 같은 Recipe가 어떻게 반복 실패하는지 화면 근거 | Align Key 재등록 여부를 정하는 현업 엔지니어 |
| **암묵지 자산화** | 엔지니어 수동 조작 → 조작 타임라인 → 한국어 절차서 | 신규 인력 교육, 절차 표준화 |
| **다음 Agent의 학습 원천(활용 목표)** | "현업 담당자는 이 화면에서 어디를 누르는가"의 시연 데이터 | Recipe Tuning·Auto Recipe Creation 개발 |

전용 PC에 알람 대응 전 건과 엔지니어가 동의한 수동 조작 세션을 축적합니다. 여기서 절차가 실제로
추출되는지를 먼저 확인하는 것이 목표입니다. 엔지니어의 설명을 함께 대조해 교육·후속 자동화에 쓸 수
있는지도 검증합니다. 지금 단계의 산출물은 자동화가 아닙니다. 의미 있는 데이터가 나오는가를 판단할
근거입니다. 키 이벤트는 별도로 수집하지 않습니다. 화면 영상만 기록하는 범위를 코드에 못박아 동의한
선을 지킵니다.

### 2.4 적용 과정의 난이도·제약·극복 방식

가장 어려웠던 지점은 화면이 계속 바뀌는 장비를 상대로 AI가 오해 없이 정확히 누르게 하는 일이었습니다. CD-SEM은 이미지를 실시간으로 측정합니다. 그래서 장비 툴 모니터의 라이브 영상이 쉬지 않고 바뀌는데 그 변화를 UI 변화나 현업 담당자의 조작으로 오인하면 잘못된 곳을 누르거나 엔지니어 개입을 잘못 감지합니다. 해법은 역할 순서였습니다. VLM이 UI와 라이브 영상 영역을 먼저 구분하면 CV가 그 안에서 정렬 위치와 이동량을 픽셀 단위로 계산합니다. 세부 대응은 아래 표에 모았습니다.

| 난이도·제약 | 극복 방식 |
|-------------|-----------|
| 라이브 SEM 영상이 계속 바뀌는 화면에서 버튼 클릭·커서 추적 | VLM이 UI 요소와 라이브 영상 영역을 구분해 위치를 잡고, CV가 정렬 위치·이동량을 계산. 녹화 분석에서는 라이브 영상 자체의 변화를 사용자 조작으로 오인하지 않도록 UI 조작과 영상 위 조작을 구분해 기록 |
| 계측 클라이언트가 표준 UI가 아니라 pywinauto 등 자동화 도구가 컨트롤을 인식 못함 | 화면 이미지 → VLM 좌표 → OCR 확인 → 클릭의 이미지 기반 제어로 전환 |
| 버튼이 빽빽한 엔지니어 도구 화면에서 단일 VLM 한 번 인식은 확률적 실패 | coarse → fine 2단계 + OCR confirm 게이트. 확인 안 되면 클릭하지 않는 fail-closed 원칙. 프롬프트 반복 시험 |
| VLM 서버 시스템 메모리 16GB 때문에 동시 구동 모델 수 제한, 재시작 시 재설치 3~4시간 | 제약이 GPU가 아니라 동시 구동 프로세스 수임을 확인. 안 쓰는 모델은 내리는 운영 원칙, 5종 → 2종 상시 운영. 실시간 루프는 판정 대부분을 CV로 처리해 VLM 호출 최소화 |
| Align Key는 픽셀 동일성을 가정할 수 없음(Lot Split·공정 Variation) | 구조·기하 기반 매칭 + 여러 매칭 방식 종합(Ensemble/RRF) + 성공 사례 consensus. 임계값은 성공·실패 점수 분포로 통계적 보정 |
| 고배율 SEM은 화면 대부분이 비슷한 선·평탄면이라 위치를 특정할 단서(선이 만나는 지점)가 드물고, 진짜 위치와 헷갈리는 가짜 후보가 많음 | 재순위 후 잔여 실패의 약 87%가 "정답이 후보에 아예 없는" 경우임을 분해로 확인. 순위 조정으로 풀리지 않는 몫은 **Align Key 재등록 권고 Recipe 목록**으로 현업과 검토 |
| 알람을 실시간으로 받을 경로가 없었음 | data-hub 적재 + h-api 연동으로 10초 간격 수신 기반 구축 |
| 개발은 Mac, 실행은 오피스 Windows. 개발 PC에서 실장비·RCS를 볼 수 없음 | 장비·API를 대체한 시험 환경으로 실장비 없이 자동 테스트. 재생(replay) 절차로 알람 없이 사이클 강제 실행. 오피스 실행 결과는 한 줄 요약으로 회수 |
| 얼라인 위치 재설정은 오동작 시 측정에 영향 | 점검 모드(비파괴) → 반자동(확정은 현업 담당자) → 전용 PC에서 현업 엔지니어와 합동 시험 → 26대 실전 배치의 단계적 게이트. 뒷정리(녹화 종료·창 닫기·팝업 정리)는 예외 시에도 순서대로 시도 |
| 다른 엔지니어가 장비를 점유 중일 수 있음 | 점유 3상태 판별, 화면 공유 요청 후 관전 녹화, 쿨다운 후 재시도. 엔지니어 개입 감지 시 자동화가 물러남 |
| AI와 엔지니어가 같은 장비·같은 PC를 동시에 다룰 때의 충돌(아래 별도 정리) | 공존 규칙을 현업과 정하고, 전용 PC·AI용 ID로 환경을 분리해 규칙을 구현 중 |
| 실보정 적용 과정에서 화면 영역 확보 조건 때문에 보정 단계가 실행되지 않던 병목 발견 | 점검 모드에서 검증된 라이브 화면 영역 검출을 보정 경로에도 적용해 병목 제거. 같은 검출에서 촬영 모드도 읽어 "모든 화면을 SEM으로 가정"하던 조용한 오류 제거 |

**AI와 엔지니어가 함께 일할 때 생긴 문제와 정한 규칙**

지금까지는 엔지니어 개인 PC에서 AI를 돌리며 현업 MI 엔지니어와 합동 평가를 했습니다. 이 과정에서 AI 혼자 도는 환경에서는 보이지 않던 상황이 드러났습니다. 대응 필요성을 정리해 규칙으로 합의했습니다.

| 합동 평가에서 확인하거나 대응 필요성을 정리한 상황 | 정한 규칙 |
|------------------------------------------------------|-----------|

- **자체 AI 운영 역량**: 외부 API 의존 없이 사내 HCP에서 화면 이해 AI를 배포·벤치·교체하는 체계.

**확산 가능성: Auto Recipe Creation의 시작점**

MI 조직의 장기 목표는 Auto Recipe Creation(측정 설정 작성 자동화)입니다. MI 엔지니어들은 업무 시간의
상당 부분을 Recipe 작성에 씁니다. 이 일을 AI가 상당 부분 맡을 수 있다면 조직 전체의 생산성이 크게
바뀝니다. 단계는 이렇게 이어집니다.

1. **지금: Align Tuning Agent** = Align Fail 발생 시 정렬 위치를 다시 맞추는 반자동 대응 시스템(이 사례).
2. **2027: Recipe Tuning 자동화** = 여기서 확보한 화면 인식·조작 기반을 측정 설정 조정으로 확장.
3. **장기: Auto Recipe Creation** = Recipe 작성 자체의 자동화. 작성 조건 판단과 결과 품질 검증은 후속 과제.

이번 과제로 체득한 노하우가 다음 단계의 재료가 됩니다.

- **비표준 장비 화면의 이미지 기반 자동화 패턴**(VLM 좌표 → OCR 확인 → 클릭, 실시간 화면에서 역할을
  나누는 방식)을 Recipe 작성 화면 자동화의 출발점으로 재사용합니다.
- **모델 선정·프롬프트·확인 게이트의 운영 노하우**와 사내 HCP 배포 체계는 다음 Agent에 재사용됩니다.
- 소형 모델 조합이라 GPU 1~2장 규모로 26대를 모니터링하도록 설계했습니다. 장비를 늘릴 때는 모델 서비스를
  공유하되 처리량·동시 알람 규모에 따라 자원을 검증합니다. 성공 이력은 Recipe 단위(장비 무관)로 공유되므로
  신규 장비를 추가해도 기존 자산을 그대로 씁니다.
- 알람 종류는 기존 루프를 고치지 않고 얹을 수 있습니다(예: 측정 연속 실패 시 자동 중단 job이 이미 같은
  구조 위에 구현됐습니다).

**① 대응 시간: 5분 → 1분 미만 (실장비 실측)**

- *무엇을 측정했나*: 시스템이 알람을 감지한 시점(10초 주기 조회)부터 AI가 장비 화면에서 정렬 위치를 다시

- *어떻게 측정했나*: 엔지니어 개인 PC에서 실제 Align Fail 알람 3건의 감지~위치 재조정 시간을 기록으로
  확인했습니다. 기존 5분은 같은 구간(알람 인지~위치 재조정)에 대해 현업이 집계한 수동 대응 평균입니다.
- *무엇을 뜻하나*: 5분 중 현업 담당자가 하던 감지·접속·탐색·재조정이 1분 안으로 들어왔습니다. 알람 확인과

**② 정렬 정확도: 첫 후보 적중 31.8% → 76.4%**

- *무엇을 측정했나*: 멈춘 화면에서 CV 매칭 엔진이 고른 정렬 위치가 정답과 일치하는 비율입니다. rank-1은
  첫 후보가 정답인 비율입니다. 운영에서는 이 한 곳으로 재조정하므로 실제 성능에 가장 가깝습니다.
  in_topk는 후보 목록 안에 정답이 있는 비율입니다.
- *어떻게 측정했나*: Recipe 200개의 등록 이미지와 과거 실패 이미지를 내려받은 오프라인 벤치입니다. 정답
  좌표는 사람 라벨을 쓰지 않고 등록 당시 조건 정보로 산출했습니다. 성공 이미지로 기준을 만들 때는 평가
  대상을 빼는 교차검증을 적용했습니다. 실장비를 건드리지 않으므로 언제든 재실행할 수 있습니다.
- *무엇을 바꿨나*: 기준 이미지를 처음 등록한 1장에서 최근 정렬 성공 이미지 여러 장의 종합(consensus)으로
  바꿨습니다. 차이는 이 하나에서 났습니다. 지금의 Wafer 외관을 따라가는 기준이라 공정 변동에 덜
  흔들립니다. 고배율(SEM)에서는 별도 평가 세트에서 촬영 모드별 후보 재평가로 rank-1을 약 7.3%p 더
  올렸습니다.
- *촬영 모드별로 보면* (성공 사례 종합 기준, 모드별 별도 집계. 종합 지표와는 평가 집합이 달라 합산하지 않고 각각 표시합니다):

  | 촬영 모드 | 후보 포함률 | 첫 후보 적중률 | 표본 |
  |-----------|------------|---------------|------|
  | OM (저배율, Align Key가 화면의 10~20%) | 약 91.1% | 약 85.2% | 135 |
  | SEM (고배율, Align Key가 화면의 80~100%) | 약 78.9% | 약 66.5% | 185 |

  통념과 달리 고배율 SEM이 더 까다롭습니다. 화면을 크게 확대할수록 시야는 비슷한 선과 평탄면으로 채워져
  위치를 특정할 단서(선이 만나는 지점)가 드물어지고, 그 주변이 서로 닮아 진짜 위치와 헷갈리는 가짜
  후보가 많아집니다. 그래서 화면에서 촬영 모드를 읽어 모드별로 기준 이미지와 후보 평가 방식을
  바꾸도록 설계했습니다. 표본은 평가 이미지 기준입니다.
- *무엇을 뜻하나*: 오프라인 평가에서 정답 위치를 첫 후보로 고른 비율이 약 3분의 1에서 4분의 3으로
  올랐습니다. 재순위 적용 후 남은 실패의 약 87%는 정답이 후보 목록에 아예 없는 유형이어서 순위 조정만으로는
  풀리지 않았습니다. 별도 Recipe 평가로 **Align Key 재등록 검토 후보**를 도출해 현업과 대조 중입니다. 이
  수치는 오프라인 위치 탐색 지표입니다. 현장 자동 복구 성공률은 26대 배치에서 Recovery Episode로 따로
  집계합니다.

**③ 화면 조작 신뢰도: 좌표 인식+클릭 99%, 버튼 판독 100%**

- *무엇을 측정했나*: 비표준 UI의 장비 화면에서 AI가 의도한 요소를 찾아 실제로 클릭하는 데 성공한 비율,
  그리고 클릭 없이 화면의 버튼을 읽어내는 정확도입니다.
- *어떻게 측정했나*: 좌표 인식+클릭은 현업이 MAI-UI 기준으로 500회 반복 시험해 집계했습니다. 버튼 판독은
  오피스 화면 벤치(알람·클릭 없이 재실행 가능)입니다.
- *무엇을 뜻하나*: 처음에는 GUI 조작형 모델 하나가 한 번에 좌표를 찍게 했습니다. 이 방식은 확률적으로
  실패해 반복할수록 오류가 쌓였습니다. 대략 영역 → 잘라 확대해 정밀 좌표(coarse → fine)로 나눈 뒤 좌표
  인식과 클릭 시험에서 99% 성공을 확인했습니다. 운영 경로에는 OCR 라벨 확인 게이트를 더했습니다. 확인이
  안 되면 클릭하지 않고 재시도·알림으로 넘깁니다.

**④ 인프라·운영 지표**

- *모델 구성 5종 → 2종*: VLM 3종·OCR 2종을 설치해 실제 업무 화면으로 비교했습니다. 그중 VLM 1종과
  OCR 1종을 골라 상시 운영합니다. 시스템 메모리 16GB 서버에서 동시 구동 모델 수를 줄여 운영 부담을 낮췄습니다.
- *캡처 지연 234 ms → 약 1 ms*: 화면 캡처 경로에서 PNG 왕복을 없앤 뒤의 1프레임 지연 실측값입니다.
  상시 녹화의 샘플링 주기를 50 ms(초당 20프레임)로 설정할 수 있게 된 전제 조건입니다.
- *자동 테스트 1,207개*: 장비·API를 대체한 시험 환경에서 실장비 없이 도는 테스트입니다. 오피스 배포 전에
  회귀를 잡는 장치입니다. 개발 속도를 유지한 이유 중 하나이기도 합니다.

### 3.3 정량 성과 (환산·목표)

| 항목 | 값 | 산출 근거 |
|------|-----|-----------|
| 대상 장비 | R3 CD-SEM 26대 | 설치 28대 중 2대 fab-out, 실전 배치 대상과 동일 |
| 주 평균 Align Fail | 약 400~500건 (환산은 하한 400건) | 알람코드 9006, 측정 건수의 약 5% |
| 1건당 대응 시간(감지~위치 재조정) | 5분 → 1분 미만 | 실장비 실측, 4분 이상 단축 `[검증]` |
| 주당 감지~재조정 구간 장비 시간 | 약 33시간 → 약 6.7시간 (약 27시간 회수) | 400건 × 5분 → 400건 × 1분. 확정 대기·측정 재개 제외 `[목표]` |
| 환산 효과 | Wafer 약 100장/주 추가 측정 | 27시간 ÷ 15분/장 `[목표]` |
| 연간 환산 | Wafer 약 5,000장/년 | 100장 × 50주 `[목표]` |

산식은 단순합니다. 주 400건 × 건당 4분 단축 = 주 약 27시간의 장비 시간이 돌아옵니다. Wafer 1장 측정에
약 15분이 든다고 보면 주 약 100장을 더 측정할 수 있습니다. 이 값은 26대의 알람 규모 하한(400건)을
적용했습니다. 400건 전부에 같은 단축이 적용되고 확정 대기·재시도로 효과가 줄지 않는다는 가정 위의 값입니다.
실전 배치 후에는 Recovery Episode 기록으로 실제 회수 시간을 집계해 이 환산을 실측으로 바꿉니다.

**① 현업 담당자의 역할을 확정·예외 판단 중심으로 바꿀 기반이 마련됐습니다.** Fab 인라인 구성원과 MI 엔지니어는
그동안 알람을 지켜보다 접속해 화면을 뒤졌습니다. 앞으로는 AI가 맞춰 놓은 결과를 확인하고 OK를 누릅니다.
야간·교대 인계 구간에서 알람을 놓치는 부담도 줄어듭니다. 숙련자의 시간은 헷갈리는 Align Key를 다시
등록할지 판단하는 일로 옮겨 갑니다.

**② 실패가 데이터가 됩니다.** 그동안 Align Fail은 알람 이력은 남아도 실패 화면과 조치 근거는 남지 않았습니다. 이제는 실패 시점 화면,
대응 전 구간 녹화, 대응 1건마다의 기록 1줄이 남습니다. 어떤 Recipe가 반복 실패하는지, AI가 어디서
막히는지, 엔지니어는 어떻게 고치는지가 근거로 쌓여 다음 개선 순서를 정합니다. 기능은 구현했고
현장 적재는 확인 중입니다.

**③ 기술로 풀 것과 현업 담당자가 풀 것을 갈랐습니다.** 정렬 정확도 개선안은 벤치로 채택하거나 기각했습니다.
재순위 뒤에도 남은 실패는 대부분 후보 누락 유형이었습니다. 순위 조정으로는 풀리지 않는다는 것을
확인했습니다. 별도 Recipe 평가에서 SEM Recipe 104개 중 84개가 재등록 검토 후보로 분류되어 현업 대조
중입니다. 더 좋은 알고리즘을 기다릴 필요 없이 현업이 지금 할 수 있는 일이 명확해졌습니다.

**④ AI와 현업 담당자가 함께 일하는 규칙이 생겼습니다.** 합동 평가에서 장비 동작 주도권, 동시 접속 시 양보,
개입 시 자동 조작 양보, 긴급 중단, RCS 자동 복구의 필요성을 정리해 현업 담당자 우선 원칙으로 합의했습니다.
적용 개발과 검증은 진행 중입니다. 이 원칙은 후속 Agent 설계에 활용할 조직의 자산으로 정리했습니다.

**⑤ 자체 AI 운영 역량이 생겼습니다.** 외부 API 없이 사내 HCP에서 오픈웨이트 모델을 설치·비교·교체하는
체계를 갖췄습니다. 어떤 모델이 우리 화면에 맞는지는 벤치 결과로 답합니다. 모델을 바꿔도 통합
API 뒤에서 교체되므로 루프는 그대로입니다.

**⑥ 불확실한 보정은 보류하고 오측이 감지되면 후속 측정을 중단합니다.** 자동화의 정성 성과 중
중요한 것은 안 하는 판단입니다. 사전 확인 축에서는 촬영 모드를 읽지 못하면 추측해서 누르지 않고
보류합니다(틀린 모드는 틀린 기준 이미지입니다). 장비 목록에서 행을 잘못 짚었을 때는 클릭 지점의 행만
잘라 장비 ID를 문자로 확인합니다. 잘못 열린 창은 닫고 재시도합니다. 사후 감시 축에서는 보정 뒤에도
측정 과정을 지켜보다 오측이 감지되면 측정을 멈추고 담당자에게 알립니다. 엔지니어가 직접 작업에 들어가면
창 닫힘이나 측정 품질 신호로 종료를 판단합니다. 품질을 읽지 못할 때만 진행 카운터를 보조로 씁니다.
시간이 초과돼도 성공으로 단정하지 않고 관찰을 끝냅니다(오피스 확인에서 카운터가 실패 중에도 증가한다는
것을 발견해 이렇게 정했습니다). 같은 장비에서 연속 실패하면 쿨다운으로 건너뛰어 한 장비의 문제가 루프
전체를 묶지 않게 합니다. 두 축 모두 구현했고 현업 시험으로 동작을 확인 중입니다.

**⑦ 보정이 안 될 때도 현업 담당자가 다음에 무엇을 할지 알 수 있습니다.** 이전에는 보정 불가 알림이 상태 코드 한
줄이어서 엔지니어가 경로 설정을 고쳐야 하는지, Recipe를 재등록해야 하는지, 기다리면 되는지 알 수
없었습니다. 지금은 원인과 요구 행동, 참고용 매칭 점수를 함께 보냅니다. 설정 문제와 재등록 검토가 필요한
경우도 구분해 조치를 안내합니다. 대기 시간은 엔지니어가 화면 공유 요청에 응해 실제로 접속한 시점부터
다시 시작하도록 수정했습니다. 접속 판독과 대기 동작은 합동 시험에서 확인 중입니다.

**⑧ 다음 과제의 출발점이 마련됐습니다.** 비표준 장비 화면을 이미지로 자동화한 패턴, 실시간 화면에서
VLM과 CV의 역할을 나눈 방식, 프롬프트·확인 게이트 노하우, 공존 규칙이 MI 조직의 장기 목표인 Auto Recipe
Creation의 재료가 됩니다(§2.6).

| 기능 비활성화 설정(재순위·탐색 엔진·성공 사례 기준 등 주요 변경마다) | 변경 후 성능 저하 시 이전 구성으로 전환 | 운영 Runbook에 절차 기재 |
| 문서: 진행 보고서 6편, 설계 스펙·ADR, 운영 Runbook, 이슈 트래커, 도표 3장(§1) | 재현·인수인계 | 저장소 관리 |

지속 가능성의 핵심은 셋입니다. 벤치와 테스트가 실장비 없이 다시 돌아 재현할 수 있습니다. 주요 변경마다 비활성화 설정을 두어 이전 구성으로 되돌릴 수 있고, 대응 1건이 기록 1줄로 남아 기록을 축적할 구조도 있습니다(현장 적재는 확인 중). 2명이 7.5개월간 만든 시스템이지만 이 셋 덕분에 담당자가 바뀌어도 이어받을 수 있습니다.

### 3.6 업무 난이도와 혁신의 의미

- **난이도**: 자동화 대상이 비표준 UI + 매번 달라지는 정답 + 계속 바뀌는 라이브 영상이라
  기존 UI 요소 인식 방식으로는 자동화가 어려웠습니다. 여기에 이미지 기반 AI로 자동화 경로를
  구현했고, 현업 담당자와 AI가 같은 장비를 다루는 운영 문제까지 풀어야 했습니다.
- **혁신의 방식**: 반복 조작은 자동화 기반으로 옮기고 정밀 좌표(CV)와 확정·예외 판단(현업 담당자)의
  책임을 분리했습니다. 화면 이해와 문자 확인은 소형 AI 모델 2종(VLM·OCR)이 맡고 정밀 판정은 CV가 맡았습니다. 이 분담 덕분에
  거대 모델 없이 GPU 1~2장으로 26대를 모니터링하도록 설계할 수 있었습니다.
- **기술과 협업의 경계**: 개선안은 벤치로 채택·기각했습니다. 재순위 적용 후 남은 실패 중 약
  87%가 정답이 후보에 없는 유형임을 확인해 Align Key 재등록이라는 현업 협업 과제로 연결했습니다.
  AI가 못 푸는 몫을 숨기지 않고 현업 담당자의 과제로 정의했습니다. 이것이 이 사례의 성과입니다.

## 4. SKMS 기본 정신

> 두 정신을 선택했습니다. 정의는 SKMS 전문(2020년 14차 개정, sk.co.kr 공개본)과 SK AX 기업문화 페이지의
> 공개 문구를 참고했으며, 직접 인용은 따옴표로 표시했습니다. 사내 공식 판본과의 대조는 제출 전 확인합니다.

### 4.1 패기 — 일과 싸워서 이기는 힘

**SKMS의 정의**

> "자발적·의욕적 두뇌활용이 외부로 발현되는 모습이 곧 일과 싸워서 이기는 패기이다. 패기 있는 구성원은
> **스스로 동기부여하여 문제를 제기하고, 높은 목표에 도전하며, 기존의 틀을 깨는 과감한 실행**을 한다. 그
> 과정에서 **필요한 역량을 개발**하기 위해 노력하며, 타 구성원과 함께 적극적으로 소통함으로써 더 높은
> 성과를 낸다. 패기 실천 환경도 구성원 스스로 조성할 때 가장 효과적이다." (SKMS 전문, VWBE 문화)

**우리 사례에서의 패기**

- **반복 업무를 자동화 과제로 정의했습니다.** Align Fail 대응은 오랫동안 현업 담당자가 하는 일이었습니다. 주
  400~500건, 건당 5분, 24시간 교대 대응이라는 부담을 먼저 수치로 세웠습니다. 계측 장비 화면은 표준 컨트롤
  인식이 어려워 기존 자동화 도구로 풀기 힘들었는데, 이 사실을 안 되는 이유가 아니라 풀어야 할 문제로 다시
  정의해 검증을 시작했습니다. 목표는 알림 자동화 같은 부분 개선이 아니었습니다. 감지·재조정·기록을
  자동화하고 최종 확정만 현업 담당자가 맡는 루프였습니다.
- **적절한 AI를 찾기 위해 탐색하고 영역별로 시험했습니다.** 외부 솔루션을 기다리지 않고 Hugging Face의
  오픈웨이트 최신 모델 여러 종을 사내 HCP에 직접 설치해 실제 업무 화면으로 비교했습니다. 화면 이해 VLM
  3종과 OCR 2종을 업무 과제별로 시험했습니다. 비교 결과와 운영 자원 제약을 보고 좌표 인식은 MAI-UI, 문자
  확인은 PaddleOCR-VL을 상시 운영 모델로 정리했습니다. 모델 선택이 감에 기대지 않고 벤치 결과를 따르는
  체계도 이 과정에서 자리 잡았습니다.
- **VLM만으로 안 되는 영역은 CV를 동원해 보완했습니다.** VLM은 화면을 이해하지만 정렬에 필요한 픽셀 정밀도와
  반복 가능한 점수는 약합니다. 그 영역을 VLM에 억지로 맡기지 않고 컴퓨터 비전 매칭 엔진을 붙였습니다. VLM은
  어디를 볼지 정하고 CV는 정확히 몇 픽셀인지 재도록 역할을 나눴습니다. VLM의 벽을 만났을 때 목표를 낮추지
  않고 도구를 더했습니다.
- **시행착오를 평가로 바꿨습니다.** 처음 시도한 단일 GUI 조작형 모델은 좌표가 어긋나고 반복할수록 오류가
  쌓였습니다. 그래서 판단을 두 단계(coarse → fine)로 나누고 OCR 확인을 붙였습니다. 정렬 정확도 개선안은
  오프라인 벤치에서 하나씩 A/B로 시험했습니다. 핵심 개선 두 축(성공 사례 종합, 촬영 모드별 후보 재평가)을
  채택하고 나머지는 평가 결과에 따라 제외했습니다. 재순위 평가 방식은 투표로 섞으면 성능이 낮아졌고, 그래서
  촬영 모드에 따라 선택하도록 바꿨습니다. 실장비 적용 과정에서는 화면 영역 확보 실패로 보정 단계가 실행되지
  않던 원인을 확인하고 제거했습니다.
- **필요한 역량을 프로젝트를 통해 축적했습니다.** VLM 서빙과 벤치, 프롬프트 설계(화면의 기준 단서를 먼저
  찾도록 지시), Windows GUI 제어, CV 매칭, 실시간 화면에서 변화를 가려내는 일까지 7.5개월 동안 현장 시험과
  함께 쌓았습니다.
- **예외 처리와 재검증 체계를 마련했습니다.** 자동화가 대체로 되는 것과 장비에 붙여도 되는 것은 다릅니다.
  확인되지 않은 클릭은 나가지 않는 fail-closed 원칙을 세웠습니다. 예외가 나도 녹화 종료·창 닫기·팝업 정리는
  시도하도록 뒷정리를 붙였습니다. 실장비 없이 도는 자동 테스트 1,207개, 주요 변경마다 되돌릴 수 있는 설정도
  함께 갖췄습니다.
- **실천 환경을 스스로 조성했습니다.** 개발 PC(Mac)에서는 실장비를 볼 수 없었습니다. 이 제약은 장비·API를
  대체한 시험 환경과 기록된 조건으로 반복 시험하는 절차로 넘었습니다. 현업 담당자와 AI가 같은 장비를 다루는 문제를
  만나자 전용 PC를 확보했고 AI용 ID 할당과 공존 규칙 적용을 진행하고 있습니다.

### 4.2 Teamwork — 다른 팀이 같은 팀처럼

**SKMS의 정의**

> "회사는 **조직화된 힘**을 통해 가용자원을 효과적으로 활용하여 최대한의 가치를 창출하는 공동체이다."
> "패기 있는 구성원은 … **타 구성원과 함께 적극적으로 소통**함으로써 더 높은 성과를 낸다." (SKMS 전문)

SK AX 기업문화 페이지는 이를 회사의 조직화된 힘으로 구성원 전체의 행복을 키워 나가면 각자의 행복도 더
커진다는 믿음으로 풀어 설명합니다. 이 사례에서는 두 조직의 자원을 하나의 목표에 조직화하고
서로 적극적으로 소통한 것을 Teamwork로 봅니다.

**우리 사례의 Teamwork**

- **기반기술전략 AX Part와 R&D DMI NAND MI기술이 같은 팀처럼 일했습니다.** 소속이 다른 두 팀이지만
  실시간으로 소통하며 시험하고 개발했습니다. AX 쪽이 기능을 고치면 현업이 곧바로 장비에서 시험했습니다.
  거기서 발견한 미진한 부분을 다시 고쳐 같은 조건에서 재시험하는 사이클이 프로젝트 내내 돌았습니다.
  투입 인원은 각 1명, 합쳐 2명입니다.
- **현업 엔지니어가 시험 환경을 만들어 줬습니다.** MI 엔지니어는 시험용 Wafer와 Recipe를 골라 장비 사용
  인가를 받았습니다. Align Fail이 실제로 나는 시험 환경을 구축해 AI가 곧바로 들어가 시험할 수 있게 설정을
  도왔습니다. 실알람은 기다려야 오지만 이 재현 환경 덕분에 알람 발생을 기다리지 않고 기능을 확인할 수
  있었습니다.
- **현업의 암묵지가 판단 규칙으로 들어가는 구조입니다.** 이 시스템은 코드만으로 완성되지 않습니다. "이
  화면에서는 왜 이렇게 해야 하는가"라는 MI 장비 엔지니어의 지식이 AI의 판단 규칙에 들어가야 합니다.
  - 현장 시험에서 측정 카운터가 측정이 실패하는 중에도 계속 증가한다는 것을 확인하고 엔지니어 작업
    완료 판정을 측정 품질 신호 우선·카운터 보조로 바꿨습니다.
  - 저배율(OM)과 고배율(SEM)에서 Align Key가 화면에 차지하는 비율과 실패 양상이 다르다는 장비 특성을
    고려해 A/B 평가로 모드별 후보 평가 방식을 결정했습니다.
  - 재순위만으로 풀리지 않는 후보 누락과 등록 Key의 구별력 문제는 벤치로 확인했습니다. 재등록 검토
    후보를 도출하는 도구를 만들고 실제 대상과 판단 기준은 현업과 검토할 과제로 정리했습니다. AI가 못 푸는
    몫을 숨기지 않고 현업의 과제로 함께 정의했습니다.
- **현업 담당자와 AI가 함께 일하는 규칙을 함께 합의했습니다.** 개인 PC 시험과 합동 평가에서 장비 동작 주도권,
  동시 접속 시 양보, 개입 시 자동 조작 양보, 긴급 중단, RCS 자동 복구의 필요성을 두 팀이 정리해 현업 담당자 우선
  원칙에 합의했고 적용 개발과 검증을 진행 중입니다. 엔지니어가 개입하면 자동화가 물러나도록 한 것은 현업과
  합의해 기술 설계에 반영한 운영 규칙입니다. 이 원칙은 후속 Agent 설계에도 활용할 수 있도록 정리했습니다.
- **분리된 개발 환경을 소통 리듬으로 이었습니다.** 개발은 Mac, 실행은 오피스 Windows라 개발자는 실장비
  화면을 볼 수 없습니다. 현업이 장비 시험 결과와 실행 로그·화면 증거를 전달하고 개발자가 수정한 뒤 현업이
  같은 조건에서 재시험하는 방식으로 협업했습니다.
- **두 조직의 자원을 결합했습니다.** AX Part의 AI 개발·운영 역량과 MI의 장비 지식·시험 환경이 하나의 목표에
  조직화된 덕분에 2명이 7.5개월에 감지에서 기록까지 도는 루프를 만들고 26대 실전 배치를 준비하고 있습니다.

## 5. Operation Improvement with AI

### 5.1 기존 프로세스의 불편함

| 유형 | 반복 손실 | 개선 방향 |
|------|-----------|-----------|
| **수작업** | 알람 확인 → RCS 실행·로그인 → 장비 목록 탐색 → 접속 → Align Key 탐색(배율 변경) → 재조정 → 확정. 매 건 같은 순서를 현업 담당자가 반복 | 반복 입력·조작 |
| **중복 확인** | 같은 Recipe의 같은 실패를 장비마다·시간마다 다른 담당자가 처음부터 다시 판단. 이전 조치의 화면·판단 근거를 재사용하기 어려움 | 동일 Recipe 이력 재사용 |
| **숙련도 의존** | 멈춘 화면에서 Align Key를 찾는 시각 판단과 재조정 정밀도가 개인 경험에 좌우. 고배율 화면은 위치를 특정할 단서가 드물어 헷갈리는 Key는 숙련자도 오판할 위험 | 판단 기준 명문화 |
| **처리 지연** | 감지가 현업 담당자의 확인 주기에 의존. 야간·교대 인계 구간에 지연되고, 수동 감지~재조정 평균 5분의 홀드가 건마다 쌓여 계측 WIP이 밀림 | 대응 소요 시간 단축 |
| **오류 가능성** | 잘못된 위치를 선택한 채 확정할 위험. 화면 기록이 없어 사후 원인 추적과 재발 확인이 어려움 | 사전 확인·사후 감시·증거 보존 |

절차 자체는 정형화되어 있었습니다. 24시간 발생하는 알람은 Fab 인라인 구성원과 MI 엔지니어가 나눠 대응했고 이런 반복 부담과 편차는 화면을 보고 판단하는 단계와 조작 정밀도에서 생겼습니다(§2.1).

### 5.2 AI로 인한 변화 지점

| AI·자동화 기능 | 적용 지점 | 무엇이 달라지나 |
|----------------|-----------|-----------------|
| **탐지** | 사내 알람 연계 API를 10초 주기로 조회해 Align Fail(9006)만 선별하고 신규 발생 시점에 1회 발동(규칙 기반). 접속 후 화면에서 라이브 SEM 영역·촬영 모드(OM/SEM)·타인 점유 여부를 VLM으로 판독 | 주기적인 알람 확인이 자동화되고, "지금 화면이 어떤 상태인가"를 시스템이 먼저 읽음 |
| **자동 대응** | RCS 실행·로그인·장비 선택·접속 → 상시 녹화 → 성공 사례 종합 기준(부족·저품질이면 등록 이미지)으로 CV 매칭 → 재정렬 → 확정 요청 알림 → 현업 담당자 OK → 완료 감시(창 닫힘 또는 측정 품질 신호 우선, 카운터는 판독 불가 시 보조, 시간 초과는 성공으로 보지 않고 관찰 종료) → 자동 종료 | 실장비에서 감지~위치 재조정이 1분 미만. 최종 확정은 현업 담당자가 수행하며 확정 대기·완료 감시·종료 시간은 별도 |

| **이상치 필터(입력·화면 상태 검증)** | 실행 전: 좌표 미검출·OCR 라벨 불일치·금지 문구면 클릭 차단, 촬영 모드 불명이면 보정 보류, 잘못 열린 장비 창 감지·닫기. 실행 후: 보정 뒤 오측 감지 시 후속 측정 중단, 연속 실패 장비 쿨다운 | 불확실한 조작은 보류하고 오측이 감지되면 후속 측정을 중단하도록 구현. 현업 시험으로 동작 확인 중 |
| **Agent 실행** | 위 과정을 한 루프로 실행하되 확정·예외는 현업 담당자에게 넘기는 반자동 구조. 실패 시 재시도·대체 경로·쿨다운, 타인 점유 시 관전 녹화로 전환, 현업 담당자 개입 시 자동 조작 양보, RCS 부재 시 재실행·재로그인, 긴급 중단 단축키 | 정상 경로는 자동 진행하고, 현업 담당자는 확정과 예외 판단을 맡음 |
| **엔지니어 암묵지 자산화** | 알람 대응 전 구간 상시 녹화 + 엔지니어 동의 아래 수동 조작 세션 녹화 → 조작 타임라인 → 한국어 절차서 변환 경로 구현. 현업 설명과 대조해 판단 이유를 정리하고 활용 가능성을 검증 | 개인 경험으로만 있던 조작 절차가 기록·절차서로 남을 경로 확보(현장 추출·활용 검증 진행 중) |
| **요약·알림** | 보정 불가 시 원인·요구 행동·매칭 점수를 담아 알림. 설정 문제와 Recipe 재등록 검토를 구분. 대응 1건의 시도·판정·결과를 한 줄로 구조화(Recovery Episode, 현장 적재 확인 중) | 현업이 다음 행동을 판단할 근거를 제공 |
