# PagedAttention과 Prefix Caching 메모 (2026-03-17)

## 목적

이 문서는 아래 두 질문에 짧고 실무적으로 답하기 위한 메모다.

1. `PagedAttention`은 무엇인가?
2. `prefix caching`은 무엇이고, 언제 효과가 큰가?

둘 다 `vLLM` 같은 추론 런타임에서 **긴 프롬프트와 여러 동시 요청을 더 효율적으로 처리하기 위한 최적화**다. 다만 해결하는 문제는 서로 다르다.

## 한 줄 요약

- `PagedAttention`: **KV-cache를 메모리 안에서 더 잘 저장하고 관리하는 방법**
- `prefix caching`: **이미 계산한 prefix의 KV-cache를 다음 요청에서 다시 쓰는 방법**

즉, 전자는 **메모리 배치 전략**, 후자는 **계산 재사용 전략**에 가깝다.

## 1. 먼저: KV-cache가 왜 중요한가

LLM은 입력을 한 번 읽고 끝나는 모델이 아니다. 프롬프트를 읽는 `prefill` 단계와, 다음 토큰을 하나씩 생성하는 `decode` 단계를 거친다. 이때 각 레이어의 attention 계산 결과 중 다음 토큰 생성에 다시 써야 하는 값들을 보관하는데, 이것이 보통 `KV-cache`다.

`K`는 key, `V`는 value를 뜻한다. 긴 프롬프트나 긴 대화, 동시 요청이 많을수록 이 캐시가 커진다. 실제 서빙에서는 모델 weight 자체도 크지만, **요청별 KV-cache가 GPU 메모리를 많이 잡아먹는 것**이 병목이 되기 쉽다.

## 2. PagedAttention

### 2.1 무엇인가

`PagedAttention`은 KV-cache를 큰 연속 메모리 덩어리로 다루지 않고, **작은 block/page 단위로 쪼개서 관리하는 방식**이다. 개념적으로는 운영체제의 virtual memory paging과 비슷하다.

기존 단순 구현은 요청마다 "이 요청의 KV-cache 공간"을 크게 잡아두는 식이 되기 쉽다. 그런데 실제 생성 길이는 요청마다 다르고, 어떤 요청은 빨리 끝나고 어떤 요청은 오래 간다. 그러면 GPU 메모리 안에 자투리 공간이 많이 생기고, 큰 연속 공간을 확보하기도 어려워진다. 이것이 fragmentation 문제다.

`PagedAttention`은 이 문제를 줄인다.

- KV-cache를 고정 크기 block들로 나눈다.
- 요청은 필요한 block만 가져다 쓴다.
- 생성이 길어지면 block을 더 붙인다.
- 요청이 끝나면 해당 block만 반납한다.

이 방식의 핵심 이점은 아래와 같다.

- 메모리 fragmentation이 줄어든다.
- 같은 GPU 메모리로 더 많은 요청을 동시에 처리할 수 있다.
- 긴 요청과 짧은 요청이 섞여 있어도 메모리 활용률이 좋아진다.
- 결과적으로 batch를 더 크게 유지하기 쉬워지고 throughput이 올라간다.

### 2.2 비유

연속 메모리 방식은 "손님마다 큰 방 하나를 통째로 예약"하는 것에 가깝다. 손님이 방 절반만 써도 나머지 절반은 비어 있지만 다른 손님이 쓰기 어렵다.

`PagedAttention`은 "작은 객실 여러 개를 필요할 때만 배정"하는 방식에 가깝다. 그래서 낭비가 적고 회전이 좋다.

### 2.3 무엇을 개선하지는 않는가

`PagedAttention`이 모델 자체의 정확도를 높이는 것은 아니다. 주된 효과는 아래 쪽이다.

- 메모리 효율
- 동시성
- 처리량
- OOM 가능성 완화

즉, "더 똑똑하게 답하게 만든다"기보다 "같은 GPU로 더 안정적으로 많이 돌린다"에 가깝다.

## 3. Prefix Caching

### 3.1 무엇인가

`prefix caching`은 여러 요청이 **앞부분 prefix를 공유할 때**, 그 구간의 KV-cache를 재활용하는 최적화다.

예를 들어 아래 요청들은 prefix가 상당 부분 같다.

- 같은 system prompt를 공유하는 채팅 요청들
- 같은 긴 지침문 뒤에 사용자 질문만 조금씩 달라지는 요청들
- 같은 GUI 조작 규칙을 앞에 붙이고, 마지막 스크린샷 설명만 바뀌는 VLM 요청들

이 경우 매번 prefix 전체를 다시 `prefill`하면 중복 계산이 많다. `prefix caching`은 이전 요청에서 만들어 둔 prefix 구간의 KV-cache를 찾아서 재사용하고, **새로 달라진 부분만 추가 계산**한다.

### 3.2 왜 빠른가

LLM 추론에서 긴 프롬프트는 `prefill` 비용이 크다. 특히 system prompt나 규칙 프롬프트가 길수록 같은 내용을 매번 다시 읽는 비용이 무시되지 않는다.

`prefix caching`이 잘 맞는 경우 효과는 아래처럼 나타난다.

- 첫 토큰이 더 빨리 나온다.
- 긴 공통 프롬프트를 반복할 때 GPU 계산량이 줄어든다.
- 같은 정책 프롬프트를 공유하는 다수 요청에서 처리량이 좋아진다.

### 3.3 비유

매번 같은 교과서 1장부터 100장까지 다시 읽고 마지막 101장만 다르게 읽는 대신, 1장부터 100장까지의 독해 결과를 저장해 두고 101장만 새로 읽는 것과 비슷하다.

### 3.4 조건과 한계

`prefix caching`은 아무 요청에서나 자동으로 크게 이득이 나는 것은 아니다.

- 공통 prefix가 실제로 길어야 효과가 크다.
- prefix가 조금이라도 달라지면 재사용 범위가 줄어든다.
- tokenizer/chat template가 달라지면 같은 문장처럼 보여도 토큰 시퀀스가 달라질 수 있다.
- 이미지 자체가 바뀌는 멀티모달 요청에서는 텍스트 prefix는 재사용되어도 전체 입력 비용이 모두 사라지는 것은 아니다.

즉, `prefix caching`은 "반복되는 텍스트 앞부분"이 많은 워크로드에서 특히 잘 맞는다.

## 4. 둘의 차이

둘은 함께 쓰이지만 역할이 다르다.

| 항목 | PagedAttention | Prefix Caching |
|------|----------------|----------------|
| 핵심 문제 | KV-cache 메모리 낭비와 fragmentation | 같은 prefix의 중복 계산 |
| 주된 이점 | 메모리 효율, 동시성, throughput | prefill 절감, 응답 시작 속도 개선 |
| 재사용 대상 | block/page 단위 메모리 관리 | 공통 prefix의 KV-cache |
| 잘 맞는 상황 | 동시 요청이 많고 길이가 제각각인 서빙 | 긴 system prompt를 반복하는 요청 패턴 |

짧게 말하면:

- `PagedAttention`은 "KV-cache를 어디에, 어떻게 담을까"의 문제다.
- `prefix caching`은 "이미 계산한 prefix를 다시 쓸 수 있을까"의 문제다.

## 5. 이 저장소 관점에서의 의미

우리 저장소의 `poc/work2` 흐름처럼 **고정된 지침 프롬프트 + 매 요청마다 바뀌는 스크린샷/상황 설명** 구조가 반복되면 `prefix caching`의 이득을 기대할 수 있다.

예를 들면 아래 같은 패턴이다.

- 로그인 화면 분석 프롬프트는 거의 고정
- 메인 탭 분석 프롬프트도 대부분 고정
- 바뀌는 것은 현재 screenshot과 소량의 상태 텍스트

이때 공통 지침 prefix를 반복해서 다시 계산하지 않으면 응답 지연을 줄이는 데 도움이 된다.

반면 `PagedAttention`은 특정 프롬프트 구조보다는 **서버 전체의 메모리 운영 안정성**에 더 직접적이다. 여러 사용자나 여러 자동화 단계가 동시에 붙을수록 체감 이점이 커진다.

## 6. 실무 판단 기준

- 단일 요청 latency가 느리고, 긴 고정 프롬프트를 반복한다면 `prefix caching` 효과를 먼저 본다.
- 동시 요청이 늘 때 OOM이나 batch 축소가 잦다면 `PagedAttention`의 가치가 더 크다.
- 대부분의 실제 서빙에서는 둘 중 하나만 중요한 것이 아니라, **둘이 같이 있어야** 긴 프롬프트와 다중 요청을 안정적으로 감당하기 쉽다.

## 결론

`PagedAttention`과 `prefix caching`은 모두 "LLM을 더 싸고 빠르게 돌리기 위한 런타임 최적화"지만 초점이 다르다.

- `PagedAttention`은 KV-cache를 page/block 단위로 관리해서 GPU 메모리 낭비를 줄인다.
- `prefix caching`은 공통 prefix의 KV-cache를 재사용해서 중복 prefill 계산을 줄인다.

따라서 긴 지침 프롬프트가 많은 GUI/VLM 자동화 워크로드에서는 `prefix caching`이 latency 개선에 직접적이고, 다중 요청 환경에서는 `PagedAttention`이 전체 처리 안정성과 throughput에 직접적이다.
