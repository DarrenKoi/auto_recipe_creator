01 / THE BIG PICTURE

먼저, 두 가지 질문을 연결합니다

녹화 분석의 질문

“이 녹화에서 무엇이 보였고, 사람이 어떤 행동을 했으며, 이후 무엇이 바뀌었는가?”

산출물: 근거를 따라갈 수 있는 Recovery Trace

워크플로의 질문

“다음에 어떤 상태가 관측되면 이 행동을 선택하고, 무엇으로 성공을 확인할 것인가?”

산출물: 조건이 있는 Recovery Playbook

1 · 관측원본 프레임시각과 화면 영역, 가능하면 입력 기록을 함께 보존
2 · 추출상호작용 타임라인변화 구간, 클릭·입력 후보, 대상과 전후 화면 연결
3 · 정규화의미 단위 행동위치 보정·탐색·배율 설정·정렬 확인으로 분류
4 · 근거 연결Recovery Trace상태·행동·검증을 사건 단위로 묶고 수행자가 검토
5 · 통합조건부 Playbook여러 기록에서 적용 조건과 성공·실패 경로 도출
6 · 변환·평가workflow_4 그래프승인된 구조를 노드와 분기로 변환하고 shadow 평가

현재 코드가 담당하는 부분

구성 요소확인한 역할
recording_filter프레임 변화 분석, 클릭·입력 추정, OCR/VLM을 통한 대상 식별, 타임라인 생성
workflow_extract규칙 기반으로 이벤트를 step으로 묶어 workflow.json과 workflow.md 생성. 그룹화 자체는 VLM 없이 동작
workflow_4/framework노드, 성공·실패 경로, 재시도를 표현하는 상태 머신과 실행 엔진

다음에 채워야 할 연결: 추출한 step에 행동 전 상태, 도메인 행동 의미, 검증 결과를 연결하는 일입니다. Playbook 분류·검토·컴파일·shadow의 전체 경로는 명세상 목표이며, 모두 구현됐다는 뜻은 아닙니다.

02 / OBSERVE

행동 전후 프레임을 한 묶음으로 읽습니다

각 프레임의 설명문을 나열하기보다 직전 → 행동 중 → 직후를 비교합니다. 이렇게 해야 “버튼이 보인다”에서 “버튼을 조작한 뒤 상태가 바뀌었다”로 넘어갈 수 있습니다.

추출할 정보예시주된 수단
화면 상태SEM Monitor, 확인창, 컨트롤의 표시 여부영역 탐지·CV, 필요시 VLM
읽을 수 있는 값배율, 상태 문구, 측정 진행값OCR
영상 내 관계recipe key 위치, crosshair와의 거리matcher·좌표 계산
상호작용더블클릭 후보, 배율 선택, 확인 클릭입력 기록 우선, 없으면 영상 추정
행동 후 변화목표 위치 이동, 배율 변경전후 프레임 비교
최종 결과측정 재개, 재실패, 관측 불가상태·측정 신호 검증

프레임을 줄일 때 지킬 것

SEM 영상과 UI 영역의 변화량을 따로 봅니다. 영상 전체의 변화가 작아도 상태 문구나 확인 버튼 주변의 변화는 중요할 수 있습니다. 원본은 보존하고, 분석용 대표 프레임을 고르되 행동 전후 구간을 함께 남깁니다.

사실과 추정을 함께 저장하기

각 판독에 시간·근거 프레임·대상 영역·판독 출처·추정 여부를 연결합니다. OCR/VLM 결과는 구조화하고 필드를 검증한 뒤 사용합니다. 모델의 설명만으로 클릭이나 이동을 확정하지 않습니다.

프레임만으로 확정할 수 없는 것: 정확한 클릭 횟수, 보조키, 보이지 않는 입력, 사람의 의도입니다. 화면이 바뀌었다는 사실은 남기되, 확인되지 않은 상호작용은 후보로 유지합니다. 숫자로 표현한 신뢰도만으로 실행 가능성이 보장되지는 않습니다.

03 / NORMALIZE

서로 다른 조작을 같은 행동 의미로 묶습니다

사람마다 커서 경로나 클릭 수가 달라도 같은 목적의 조작을 할 수 있습니다. 재사용할 단위는 위치 재지정, FOV 탐색, 배율 설정, 정렬 확인과 같은 도메인 행동입니다.

녹화에서 보이는 근거행동 후보추가로 확인할 것
영상의 특정 위치 더블클릭 후 위치 변화reposition_to_align_key전후 key 위치, 다음 의미 단계가 정렬 확인인지
영상 영역에서 탐색 이동pan_fov이동 방향·크기와 조작 문맥
배율 컨트롤 조작 후 읽을 수 있는 값 변경set_magnification변경 후 절대 배율 값
확인 컨트롤 클릭confirm_align실제 대상 컨트롤의 식별

더블클릭 한 장면만으로 위치 보정이라고 결정하지 않습니다. 앞뒤 화면과 다음 행동을 함께 봐야 탐색 이동과 최종 위치 지정을 구분할 수 있습니다. 구분되지 않으면 unclassified로 남깁니다.

원본 근거에 보존

클릭 좌표, 프레임 번호, 시간 구간, 원본 이벤트 ID를 남깁니다. 현재 그룹화 코드는 raw_events로 원본 이벤트를 연결합니다.

재사용할 행동에 표현

목표를 matched_recipe_box_center처럼 의미로 표현합니다. 실행 시점의 좌표는 현재 화면에서 다시 찾습니다.

자동 분류는 검토할 제안입니다. 실제 행동 수행자가 근거를 확인해 의미를 확정합니다. 마지막에 복구가 성공했다는 이유만으로 앞선 모호한 조작의 의미를 소급 확정하지 않습니다.

04 / GUARD & VERIFY

언제 행동하고, 무엇으로 확인할지 정의합니다

각 행동에 진입 조건과 행동 후 검증을 붙입니다. 아래는 구조를 설명하기 위한 예시이며, 실제 기준과 임계값은 관측 근거와 장비 검증으로 정해야 합니다.

규칙의 구성위치 보정 예시
진입 조건 · Guardrecipe key가 식별되고 현재 crosshair가 목표에서 어긋나 있음
행동 · Action식별한 recipe key 중심으로 위치 재지정
행동 후 검증 · Verification새 프레임에서 목표 위치와 crosshair의 관계 확인
다음 단계확인 컨트롤이 관측되면 정렬 진행 후 결과 관측
사건의 결과 · Outcome측정 재개 등 관측 가능한 복구 근거로 최종 판정
예외 경로key 판독 불가, 위치 검증 실패, 결과 관측 불가를 각각 처리

‘모름’을 하나의 상태로 다룹니다

조건과 검증은 true / false / unknown으로 표현합니다. 화면을 읽지 못했으면 unknown입니다. 이는 key가 없거나 행동이 실패했다는 판단과 다릅니다.

행동 시도와 복구 성공은 별개입니다. “OK를 눌렀다” 또는 “창이 닫혔다”만으로 복구 성공을 확정하지 않습니다. 최종 결과에는 측정 재개나 품질 신호처럼 관측 가능한 성공 근거가 필요합니다.

05 / BUILD THE GRAPH

여러 기록에서 분기 조건을 모읍니다

같은 상태에서 어떤 행동이 수행됐고 무엇이 확인됐는지 비교합니다. 행동 순서가 비슷해도 진입 상태나 적용 장비·레시피가 다르면 별도 규칙이 필요할 수 있습니다.

기록을 합칠 때 비교할 기준

진입 상태 · 행동의 의미와 파라미터 · 검증 결과 · 장비와 레시피의 적용 범위. 성공 사례와 함께 실패·판독 불가 사례도 수집합니다. 한 번의 성공은 그 상황의 근거이며, 다른 상황의 성공까지 보장하지 않습니다.

Trace → Playbook → Graph
Trace는 관측 기록, Playbook은 조건부 복구 모델, Graph는 승인된 구조를 엔진이 다룰 수 있도록 표현한 결과입니다. workflow_4의 일반 상태 머신과 도메인별 판정·관측 코드를 구분해 연결합니다.

06 / FIRST DELIVERABLE

첫 목표는 녹화 한 건의 검토 표입니다

기존 workflow.json의 각 step을 전후 프레임과 연결하고, 아래 항목을 한눈에 확인하도록 만듭니다. 이 표가 있어야 잘못된 추출·분류·성공 판정을 찾아 고칠 수 있습니다.

검토 항목표에 담을 내용
시간·근거전후 프레임 링크와 원본 이벤트 ID
행동 전 상태key 가시성, crosshair 관계, 배율, 컨트롤 상태
정규화 행동 후보행동 종류, 파라미터, 분류 출처, 추정 여부
행동 후 변화위치·값·화면 상태의 실제 변화
검증과 미확인 사항통과·실패·불명, 판정 근거, 수행자가 확인할 질문
  1. 한 녹화를 끝까지 연결원본 프레임 → 타임라인 → step → 전후 상태 → 결과의 연결을 확인합니다.
  2. 행동 수행자가 검토모호한 의미와 판독을 근거 프레임에 연결해 정정합니다. 근거가 없는 설명은 관측 사실과 구분합니다.
  3. 여러 Trace로 Playbook 후보 구성공통 진입 조건과 행동·검증을 묶고 실패 경로 및 적용 범위를 명시합니다.
  4. 보관된 기록으로 규칙 평가규칙 선택과 검증 판정의 일관성을 확인합니다. 같은 기록에 맞춘 규칙만 잘 통과하는지 경계하고 별도 사례에서도 평가합니다.
  5. 승인된 구조를 그래프로 변환하고 shadow 평가실제 클릭 없이 다음 행동을 예측하고, 엔지니어가 수행한 행동 및 관측 결과와 비교합니다. 기존 명세의 산출 범위는 approved-for-shadow까지입니다.

검증의 한계: 보관된 기록을 다시 평가해도 녹화에 없던 행동의 성공 여부는 알 수 없습니다. Shadow에서 예측한 행동과 실제 엔지니어 행동도 구분해야 합니다. 자동 조작의 검증은 별도 단계입니다.

첫 단계가 끝났다고 볼 기준

검토자가 각 step을 보고 “어떤 상태에서, 무엇을 했다고 판단했으며, 어떤 화면 변화로 확인했고, 무엇이 아직 불명인가”를 원본 근거까지 따라가며 설명할 수 있으면 됩니다.
