1. 큰 그림: 왜 필터링이 필요한가

capture_window_frames_tool.py 가 5분 동안 500 ms 간격으로 Tool 창을 캡처하면 약 600장의 JPEG 가 쌓인다. 이 중 대부분은 이전 프레임과 거의 동일한 "정적 화면" 이다. 팝업이 뜨거나, 다이얼로그가 닫히거나, SEM 이미지가 갱신되는 실제 "사건" 이 발생한 프레임은 전체의 5–10% 수준.

왜 미리 거르나? 다음 단계인 VLM 분석(vlm_cursor_click_filter.py 등) 은 프레임 1장당 수 초 + 비용이 든다. 600장 × VLM = 비현실적. 변화가 있는 ~50장만 VLM 에게 넘기는 것이 본 스크립트의 미션.

2. 파이프라인 한눈에 보기

JPEG 프레임 N장
→
Grayscale + Resize
→
absdiff(prev, curr)
→
threshold T=25
→
dilate 5×5 ×2
→
connected components
→
largest_blob ≥ 5000?

핵심 함수 두 개를 보면 흐름이 한눈에 보인다. 

# filter_frames_by_change.py:161-189
def _compute_change_stats(prev_gray, curr_gray, diff_threshold):
    diff   = cv2.absdiff(prev_gray, curr_gray)               # Step 2
    _, th  = cv2.threshold(diff, diff_threshold, 255,
                           cv2.THRESH_BINARY)                # Step 3
    kernel = cv2.getStructuringElement(cv2.MORPH_RECT, (5,5))
    dil    = cv2.dilate(th, kernel, iterations=2)            # Step 4

    num_labels, _, stats, _ = cv2.connectedComponentsWithStats(
        dil, connectivity=8)                                 # Step 5
    largest = max((stats[i, cv2.CC_STAT_AREA]
                   for i in range(1, num_labels)), default=0)
    return {"largest_blob_area_px": int(largest), ...}

3. Step 1 — Grayscale 로딩 & Resize

1 컬러 → 1채널 + 폭 1280px 로 축소 
image = cv2.imread(str(image_path), cv2.IMREAD_GRAYSCALE)
if w > 1280:
    image = cv2.resize(image, (1280, new_h), interpolation=cv2.INTER_AREA)
왜 그레이스케일? 변화 감지에는 휘도 정보면 충분하다. RGB 3채널 → 1채널로 줄이면 메모리·연산이 1/3. UI 변화(팝업, 텍스트 갱신)는 색상보다 밝기 차이로 충분히 잡힌다.
왜 1280px 다운샘플? 원본은 보통 2560+ 폭. absdiff 와 dilate 의 연산량은 픽셀 수에 선형 비례. 폭을 절반으로 줄이면 연산량이 1/4. INTER_AREA 보간은 다운샘플 시 모아레가 적고 평균화 효과로 노이즈도 줄여준다.

4. Step 2 — cv2.absdiff (절댓값 차이)

2 인접 두 프레임의 픽셀별 |a − b| 
diff = cv2.absdiff(prev_gray, curr_gray)

같은 위치의 두 픽셀이 동일하면 결과는 0 (검정), 다를수록 큰 값(255 = 흰색). 움직이지 않은 영역은 까맣게, 변한 영역만 밝게 떠오른다.

왜 단순 빼기가 아니라 절댓값? uint8 은 음수가 없다. a − b 가 음수가 되면 underflow 로 wrap-around(255 근처) 되어 의미가 깨진다. absdiff 는 항상 |a−b| 를 반환해 부호 문제를 회피한다.

5. Step 3 — cv2.threshold (이진화)

3 차이가 T=25 이상이면 255, 미만이면 0 
_, thresh = cv2.threshold(diff, 25, 255, cv2.THRESH_BINARY)
왜 임계값? JPEG 압축, 카메라 노이즈, 안티앨리어싱 등으로 같은 화면이라도 픽셀값이 1–10 정도 흔들린다. T = 25 미만은 "노이즈" 로 간주해 버리고, 실제 UI 변경(보통 50–255 차이) 만 남긴다.
왜 단순 binary? 후속 단계(연결요소 분석)는 0/255 이진 마스크가 필요. THRESH_OTSU 같은 적응형 방법도 가능하지만, "무변화 프레임" 의 경우 Otsu 가 노이즈를 강제로 분할해버려 false positive 가 늘어난다. 고정 임계값이 더 안전.

임계값 25는 "이 정도 차이는 노이즈" 와 "이건 진짜 변화" 의 경계선

6. Step 4 — cv2.dilate (팽창)

4 5×5 사각 커널로 2회 팽창 — 흩어진 점들을 덩어리로 
kernel  = cv2.getStructuringElement(cv2.MORPH_RECT, (5, 5))
dilated = cv2.dilate(thresh, kernel, iterations=2)

팽창은 흰색 픽셀 주변을 모두 흰색으로 채우는 모폴로지 연산이다. 5×5 커널 × 2회 ≒ 각 흰 픽셀의 영향 반경이 약 5px.

왜 팽창? 텍스트 변경 같은 작은 사건은 absdiff 결과가 수십 개의 작은 점으로 흩어진다. 그대로 connectedComponents 를 돌리면 각 점이 별도 블롭으로 잡혀 "가장 큰 블롭" 면적이 작게 나온다. 팽창은 가까운 점들을 하나의 큰 덩어리로 묶어 "실제 변화 영역" 의 크기를 제대로 측정하게 해준다.

7. Step 5 — connectedComponentsWithStats

5 흰색 덩어리를 label 단위로 분리하고 각 면적 측정 
num_labels, _, stats, _ = cv2.connectedComponentsWithStats(
    dilated, connectivity=8)

for label in range(1, num_labels):           # 0번은 배경, 건너뜀
    area = int(stats[label, cv2.CC_STAT_AREA])
    if area > largest_blob_area:
        largest_blob_area = area

connectivity=8 은 대각선으로 붙은 픽셀도 같은 덩어리로 간주. 반환되는 stats 는 [label, [x, y, w, h, area]] 행렬이며, label 0 은 배경이라 range(1, num_labels) 로 스킵한다.

왜 합계가 아닌 "가장 큰 블롭"? 화면 곳곳에 작은 변화가 흩어진 경우(예: 시계 표시가 째깍거리는 동시에 스크롤바가 미세하게 떨림) 합계는 크지만 "사건" 은 아니다. 가장 큰 단일 영역을 본다는 건 "한 곳에서 충분히 큰 일이 일어났는가" 를 묻는 것 — 팝업·다이얼로그·이미지 갱신 같은 진짜 이벤트 신호.

8. Step 6 — 면적 게이트 & 이벤트 기록

6 largest_blob_area ≥ 5000 → "change event" 
# filter_frames_by_change.py:221-232
if stats["largest_blob_area_px"] >= min_change_area_px:   # default 5000
    events.append({
        "rank": rank,
        "frame_index": ...,
        "timestamp_sec": ...,
        "frame_path": str(curr_path.resolve()),
        "prev_frame_path": str(prev_path.resolve()),
        **stats,
    })
    rank += 1

살아남은 프레임은 change_events/ 폴더에 000_frame_xxx.jpg, 001_frame_yyy.jpg 식으로 rank 순서로 복사된다. 동시에 change_events.json + summary.json 이 기록된다.

9. 파라미터 튜닝 가이드

파라미터 기본값 환경변수 높이면 낮추면
min_change_area_px 5000 FILTER_MIN_CHANGE_AREA_PX 큰 팝업만 통과 (false positive ↓) 작은 텍스트 변화도 통과 (recall ↑)
diff_threshold 25 FILTER_DIFF_THRESHOLD 노이즈 더 잘 무시 (precision ↑) 희미한 변화도 감지 (false positive ↑)
diff_resize_width 1280 FILTER_DIFF_RESIZE_WIDTH 정확도 ↑, 속도 ↓ 속도 ↑, 작은 변화 놓침
경험칙: 1280px 폭에서 5000px = 약 71×71 픽셀 정사각형. 중간 크기 다이얼로그(예: "Are you sure?" 팝업)는 가뿐히 통과하고, 진행률 표시 같은 1–2글자 변화는 보통 걸러진다.

10. 한계와 함정

  • ● 커서 움직임도 트리거된다: 마우스 커서가 큰 영역을 가로지르면 absdiff 가 굵은 흰 라인을 만들고, 팽창 후 5000px 을 넘기기 쉽다. 다음 단계인 vlm_cursor_click_filter.py 가 이걸 걸러내는 역할.
  • ● SEM 이미지 갱신은 거의 항상 통과: SEM 영상 자체가 통째로 바뀌면 면적이 수만 픽셀. 의도된 동작이지만, Tool 화면에서 SEM 이미지 영역이 차지하는 비중이 큰 경우 recipe 진행과 무관한 이미지 갱신도 다 잡힌다.
  • ● 점진적 변화는 놓친다: 프레임 간격(500 ms) 동안 매우 천천히 페이드인 되는 UI 는 인접 프레임 차이가 작아 통과하지 못할 수 있다. diff_threshold 를 낮춰도 노이즈가 같이 들어와 별로 안 풀리는 문제. 더 긴 간격(예: t vs t+5) 비교가 대안.
  • ● 전역 밝기 변화에 취약: 조명/감마 보정 같은 전역 변화는 화면 전체가 떠올라 거대한 블롭이 된다. 실제로는 "사건" 이 아닐 수 있음. 본 워크플로우는 Windows 캡처라 조명 이슈는 거의 없어 무시 가능.

요약

filter_frames_by_change.py = 매우 고전적이지만 검증된 5단계 OpenCV 파이프라인. VLM 같은 무거운 도구를 모든 프레임에 돌리지 않기 위한 저비용 prefilter 로 설계되었다.

핵심 통찰은 두 가지:

  1. 그레이스케일 + 다운샘플 + absdiff 만으로 "뭔가 바뀐 곳" 의 대략적 마스크는 거의 무료로 얻을 수 있다.
  2. 총 변화량이 아니라 가장 큰 블롭의 면적 을 보는 게 UI 이벤트 감지의 핵심. 집중된 큰 변화 = 사건, 흩어진 작은 변화 = 노이즈.
