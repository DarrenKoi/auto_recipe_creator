1. 왜 ORB 가 탄생했나

2010년 즈음의 문제 상황

  • SIFT (Lowe, 1999): 매우 강력하지만 특허로 묶여 있어 상용 SW 사용 불가. 또 128차원 float descriptor 라 매칭이 느림.
  • SURF (Bay, 2006): SIFT 의 빠른 대안. 하지만 역시 특허. 64차원 float.
  • 로보틱스/AR/모바일 응용에서 실시간 + 로열티 프리 가 절실.

2011년 Ethan Rublee 등 OpenCV Labs (Willow Garage) 가 ORB 를 발표했다. 핵심 아이디어는 단순:

  1. 이미 있는 빠른 검출기 FAST 를 가져온다.
  2. 이미 있는 빠른 descriptor BRIEF 를 가져온다.
  3. 두 알고리즘의 약점 (회전·스케일 불변성 없음) 을 영리하게 보강한다.
철학: SIFT 보다 정확하진 않지만 100배 빠르고 무료. 실용적인 응용에서는 이게 게임 체인저였다. ORB-SLAM, OpenCV stitching, AR Toolkit 등이 모두 ORB 위에 만들어졌다.

2. Step 1 — FAST keypoint 검출

FAST (Features from Accelerated Segment Test, Rosten & Drummond, 2006) 는 "corner 같은 픽셀" 을 매우 빠르게 찾는다.

알고리즘: 9-of-16 segment test

중심 픽셀 p 주변 반지름 3의 원 위에 16개 픽셀을 정의한다. p 가 corner 이려면, 16개 중 연속된 9개 이상이 모두 p보다 충분히 밝거나 어두워야 한다.

16개 주변 픽셀 중 연속 9개가 같은 방향으로 충분히 다르면 corner

왜 빠른가? — High-speed test

16개를 다 검사하면 평균적으로 느리다. FAST 는 다음 트릭으로 대부분의 비-corner 를 조기 탈락:

# 1단계 — 4개만 먼저 검사 (1, 5, 9, 13: 상/우/하/좌)
# 4개 중 3개 이상이 같은 방향으로 다르지 않으면 → 비-corner (탈락)

# 2단계 — 통과한 픽셀만 16개 segment test

# 3단계 — Non-maximal suppression
# 인접한 corner 후보 중 score 가 가장 높은 것만 남김
속도의 비결: 대부분의 픽셀은 1단계에서 탈락. 2단계까지 가는 픽셀이 1% 수준. 그래서 SIFT/SURF 의 DoG (Difference of Gaussians) 보다 수십 배 빠르다.

3. Step 2 — Harris score 로 keypoint 정렬

FAST 는 corner 를 잘 찾지만 "얼마나 좋은 corner 인가" 의 강도 정보가 없다. ORB 는 FAST 가 뽑은 후보들에 Harris corner response 를 계산해 점수로 매긴다:

R = det(M) − k · trace(M)²    where M = Σ ∇I · ∇IT

M 은 이미지 gradient 의 자기상관 행렬. R 이 크면 두 방향 모두 변화가 큰 "진짜 corner", 작으면 edge 또는 평탄. 상위 N 개 (코드의 nfeatures=2000) 만 유지.

왜 두 단계로 나누나? Harris 만 쓰면 느리다 (모든 픽셀에 행렬 계산). FAST 가 후보 픽셀 수를 1% 로 줄인 다음 그것들에만 Harris 를 계산하면 전체 속도가 빨라진다.

4. Step 3 — Image pyramid (스케일 불변성)

FAST 는 스케일 불변성이 없다. 같은 물체가 멀리서 찍히면 corner 가 사라진다. ORB 는 이미지 피라미드로 해결:

매 level 에서 이미지를 1.2배씩 작게 만들고 FAST 를 돌린다. 같은 corner 가 여러 level 에서 검출되면 스케일 불변 한 셈.

5. Step 4 — Intensity centroid 로 방향 계산

BRIEF descriptor 는 회전에 약하다. 같은 패턴을 30° 회전하면 다른 descriptor 가 나온다. ORB 의 해결책: 각 keypoint 의 방향을 미리 측정해서 descriptor 도 그 방향으로 회전시킨다.

Intensity centroid (Rosin, 1999)

Keypoint 주변 패치의 밝기 무게중심을 keypoint 중심에서의 벡터로 본다. 이 벡터의 각도가 keypoint 의 "방향".

mpq = Σ xp · yq · I(x, y)     C = (m10/m00, m01/m00)     θ = atan2(m01, m10)

6. Step 5 — BRIEF descriptor

BRIEF (Binary Robust Independent Elementary Features, Calonder 2010) 는 keypoint 주변 패치를 256-bit 이진 벡터로 인코딩한다. 핵심 아이디어는 단순:

256쌍의 픽셀 위치 (p_i, q_i) 를 사전에 정해놓고, 각 쌍에 대해:

biti = 1 if I(pi) < I(qi) else 0

이 256개 비교 결과가 그대로 256-bit descriptor.

왜 이게 통하나?

  • 회전·스케일이 같다면 같은 위치의 같은 비교를 하므로 descriptor 가 동일.
  • 밝기 전체가 변해도 비교 (대소관계) 는 보존됨 → contrast 변화에 강함.
  • 매칭이 Hamming distance (XOR + popcount) 로 끝 → CPU 의 __builtin_popcount 한 줄로 1 cycle.
속도 차이: SIFT 매칭은 128 float 의 L2 distance — 매칭 1번에 ~512 연산. BRIEF/ORB 매칭은 256 bit XOR + popcount — 매칭 1번에 ~10 연산. 50배 차이.

7. Step 6 — Rotated & Learned BRIEF (rBRIEF)

원본 BRIEF 의 2가지 약점을 ORB 가 보강:

약점 A: 회전에 약함

같은 패턴이 30° 회전하면 픽셀 쌍 (p_i, q_i) 의 위치도 30° 회전된 곳을 가리켜야 한다. 해결: 각 keypoint 의 θ (Step 4) 만큼 모든 픽셀 쌍을 미리 회전:

(p'i, q'i) = Rθ · (pi, qi)

실제로는 30개 각도 (12° 간격) 의 회전된 LUT 를 미리 만들어두고 가장 가까운 것을 선택.

약점 B: 픽셀 쌍이 서로 상관됨 (분산 낮음)

무작위 픽셀 쌍을 256개 뽑으면 일부 쌍이 거의 같은 비교를 하게 된다 (분산 0.5에서 멀어짐). 이런 비트는 정보량이 적음.

ORB 의 해법: 큰 학습 셋(약 300K 패치) 에서 가능한 모든 픽셀 쌍을 평가해서 다음 조건을 만족하는 256개를 선택:

  1. 각 쌍의 분산이 0.5 에 가까울 것 (정보량 최대)
  2. 서로 다른 쌍 간 상관계수가 낮을 것 (서로 다른 정보)

이 학습된 256쌍을 rBRIEF 라고 부른다. ORB 는 BRIEF + rotation + learned pairs.

8. Step 7 — Hamming 매칭 + Lowe ratio

Brute Force Matcher

Template 의 각 descriptor 에 대해 frame 의 모든 descriptor 와 Hamming distance 를 계산. k=2 옵션으로 최근접 2개를 받는다 (다음 단계에서 사용): 

bf = cv2.BFMatcher(cv2.NORM_HAMMING, crossCheck=False)
matches = bf.knnMatch(des_template, des_frame, k=2)
# matches[i] = [최근접, 2번째 근접]

Lowe Ratio Test (1999, SIFT 논문에서 도입)

좋은 매칭은 최근접이 2번째 근접보다 훨씬 가까워야 한다는 직관. 애매한 매칭 (1등과 2등이 비슷) 은 신뢰할 수 없으니 버린다.

match 채택 ⟺ d1 < 0.75 · d2

최근접과 2번째 근접의 거리 비율로 매칭 신뢰도 판정

왜 0.75 인가? Lowe 의 원논문 (SIFT, 2004) 에서 0.7 ~ 0.8 이 best 라고 보고. 더 보수적이면 (0.6) 매칭이 적어지고, 더 관대하면 (0.9) outlier 가 늘어남. ORB 도 같은 threshold 를 차용한다.

9. Step 8 — RANSAC homography

Lowe ratio 를 통과한 매칭에도 잘못된 쌍이 섞여 있다. 특히 반복 패턴, 텍스처 부족 영역에서 그렇다. RANSAC 이 이걸 거른다.

RANSAC 알고리즘 (Fischler & Bolles, 1981)

왜 Homography 인가?

Homography 는 평면을 평면으로 매핑하는 8 자유도 변환 (회전 + translation + scale + perspective). 4쌍의 점이면 풀 수 있다. SEM align key 가 평면이라고 가정하면 충분히 적합한 모델.

| x' | | h11 h12 h13 | | x |
| y' | = | h21 h22 h23 | · | y |
| w' | | h31 h32 1 | | 1 |

(투영 후 w' 로 정규화하면 화면상의 (x'/w', y'/w') 가 된다.)

Reprojection threshold

cv2.findHomography(..., cv2.RANSAC, 5.0) 의 마지막 인자가 5.0 인 이유: template 점을 H 로 frame 위로 옮겼을 때, 실제 매칭된 frame 점과의 거리가 5 픽셀 이하 면 inlier.

실용 팁: threshold 가 너무 작으면 (1.0) inlier 가 거의 안 나옴. 너무 크면 (20.0) outlier 도 통과. 5.0 이 일반적으로 안전한 default.

10. SIFT/SURF/AKAZE 와 비교

알고리즘DescriptorDistance속도정확도특허
SIFT (1999) 128 float L2 느림 (1×) ★★★★★ 만료 (2020)
SURF (2006) 64 float L2 중간 (3×) ★★★★ 특허 보유
ORB (2011) 256 bit Hamming 매우 빠름 (50×) ★★★ 자유
BRISK (2011) 512 bit Hamming 빠름 (40×) ★★★ 자유
AKAZE (2013) 486 bit (M-LDB) Hamming 중간 (5×) ★★★★ 자유
왜 우리는 ORB 인가? SEM 매칭에서:
  1. 매 프레임 매칭 → 속도 우선.
  2. 같은 PC 에서 다른 작업과 공유 → 리소스 절약.
  3. Chamfer 가 이미 localization 해놓음 → 정확도 보강 정도면 충분.
AKAZE 도 좋은 선택이지만 ORB 가 ~10배 빠르고, 정확도 차이는 RANSAC 이 흡수해줌.

11. 우리 코드에서의 구현

OpenCV ORB 호출 (line 241-243)

orb = cv2.ORB_create(nfeatures=2000)
kp_t, des_t = orb.detectAndCompute(template_gray, None)
kp_f, des_f = orb.detectAndCompute(frame_gray, None)

nfeatures=2000 은 "최대" 개수. 실제로는 Harris score 상위 2000개만 유지. SEM 이미지처럼 텍스처가 적은 경우 100~300개만 검출되는 게 보통.

매칭과 검증 (line 249-274)

# 1) BFMatcher (이진 → Hamming)
bf = cv2.BFMatcher(cv2.NORM_HAMMING, crossCheck=False)
raw_matches = bf.knnMatch(des_t, des_f, k=2)

# 2) Lowe ratio test
good = [m for m, n in raw_matches if m.distance < 0.75 * n.distance]
if len(good) < 8:
    return 0.0, 0, len(good)  # 최소 매칭 부족

# 3) Homography + RANSAC
src_pts = np.float32([kp_t[m.queryIdx].pt for m in good]).reshape(-1, 1, 2)
dst_pts = np.float32([kp_f[m.trainIdx].pt for m in good]).reshape(-1, 1, 2)
_H, mask = cv2.findHomography(src_pts, dst_pts, cv2.RANSAC, 5.0)

# 4) inlier ratio
inlier_ratio = mask.sum() / len(good)

Chamfer 와의 협력 (line 449-454)

# Chamfer 가 찾은 (cx, cy) 주변 1.6× 크롭만 ORB 에 넘긴다
crop, _ = _crop_with_padding(gray_frame, cx, cy, tw, th, pad=1.6)
orb_ratio, _, _ = compute_orb_inlier_ratio(template.raw_image, crop)
왜 크롭을 쓰나?
  1. 속도: 1920×1080 frame 전체보다 200×200 크롭이 100배 빠르다.
  2. 정확도: 다른 영역의 비슷한 패턴이 false match 를 만들 위험 제거.
  3. 의미: Chamfer 가 "여기" 라고 한 위치를 ORB 가 "맞다" 라고 확정하는 구조.
