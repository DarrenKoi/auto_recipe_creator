0이 지표들은 "성능 점수"가 아니라 "원인 분리(triage) 도구"다

가장 흔한 오해부터. 아래 지표들은 "우리 시스템이 몇 점이다"를 매기는 게 아니라, "매칭이 틀렸을 때 어디가 틀렸는지"를 좁히는 진단 도구다.

우리가 푸는 문제 recipe 에 등록된 align key(rcp 이미지 정중앙 영역)를, 실제 측정 이미지(msr)에서 같은 물리 위치로 다시 찾아야 한다. 그런데 S(성공) 이미지에서조차 엉뚱한 위치가 green mark 로 찍힌다. 왜?

"왜"의 후보는 여러 개다 — key 가 안 유일하다 / matcher 가 약하다 / scale 을 놓쳤다 / reference(rcp)가 낡았다(stale)… 눈으로 못 가리니 각 가설을 숫자로 분리하려고 만든 게 이 지표들이다. 그래서 지표마다 "이 값이 이러면 → 원인은 저것"이라는 판정 규칙이 붙어 있다.

핵심 사실 (오피스 실측 432장) 정답 위치(S-at-crosshair)에서조차 matcher median 점수가 0.62~0.74 수준이고, free 검색(free_best)은 S(0.66)보다 E(0.70)에서 오히려 더 높다. 정답에서 이 정도면 free 검색이 다른 곳에서 우연히 더 높게 나와 green mark 가 틀린다. = matcher 변별력(distinctiveness) 부족이 진짜 천장.

⚠️ 이 문서의 콘솔 숫자는 오피스 실측(432장, 2026-05-29)을 텍스트로 회신받은 값이다. 일부는 손전사라 자릿수 noise 가 있을 수 있으나 추세는 분명하다.

1모든 것의 기준: ground truth(S/E)와 "세 위치"

1.1 S/E 라벨 = ground truth

장비(tool)는 측정 결과를 스스로 S(success) / E(fail)로 라벨링한다(파일명 S*/E*). 이걸 정답(ground truth)으로 쓴다.

  • S 이미지: 정렬 성공 → align key 가 제 위치(보통 crosshair 위치)에 있어야 한다.
  • E 이미지: 정렬 실패 → key 를 못 찾았거나 엉뚱한 데 있다.
주의 S 라벨도 100% 믿진 않는다(feedback_doubt_s_labels). 도구의 self-report 라 false-positive 가능. 그래서 라벨은 통계의 기준으로만 쓰고, 개별 좌표 판정엔 CV 를 쓴다.

1.2 "세 위치"에서 유사도를 잰다

한 장의 msr 이미지에서 rcp-center template 을 세 군데에 대고 점수를 잰다(_process_msr).

위치뜻S 기대E 기대
at_crosshair도구가 "여기가 정답"이라 본 곳높음(E 는 crosshair 거의 없음)
at_center이미지 정중앙. 성공이면 key 가 여기 옴높음낮음
free_best이미지 전체 free 검색 best높음이동 복구 가능하면 높음
free_best 가 왜 중요한가 free_best 가 at_crosshair(정답)보다 높으면, matcher 가 정답이 아닌 다른 곳에 lock-on 했다는 직접 증거다. 정답을 알려줘도 자유 검색이 더 높은 점수를 딴 곳을 찾아냈다는 뜻 → green mark 가 틀리는 메커니즘 그 자체.

도메인 사실: E 이미지엔 crosshair 가 거의 없다(project_e_images_no_crosshair). 그래서 "E = crosshair 가 틀린 위치" 유형은 사실상 없고, E 는 순수 image-matching 으로 풀어야 한다.

2어떤 "지표(metric)"로 재나 — matcher / MI / NCC

같은 두 crop 의 닮음을 재는 방법이 여러 개다. 강점/약점이 달라 셋을 동시에 재서 "무엇이 S/E 를 가장 잘 가르나"를 비교한다.

지표코드무엇을 보나drift(밝기/대비)에
matcher (Chamfer+ORB)_scoreedge 모양(기하) 일치비교적 강건 (edge 빈약하면 약함)
MI (mutual information)_mi두 밝기 분포의 상호정보량강건 (drift 에 둔감)
NCC (정규화 상관)_nccpixel 값 선형 상관약함 (baseline 대조군)

MI: 두 이미지를 겹쳐 2D 히스토그램을 만들고 "한쪽을 알면 다른 쪽 불확실성이 얼마나 주나"를 잰다. 공정 변화로 픽셀값이 통째로 바뀌어도 구조적 대응이 남으면 높게 나온다 → 픽셀 동일성을 가정 못 하는(project_align_key_matching_constraint) SEM align 에 적합. NCC는 일부러 약한 baseline ("픽셀만 봐도 풀리나?"의 대조군).

실측에서 확인 matcher(chamfer)는 점수면이 평평해 변별력이 약했고, MI 만 약하게 변별(bACC 0.627). 그래서 recovery plan 의 Phase 3 에서 MI 를 reranker(후보 재정렬기)로 채택하는 방향이 나왔다.

3S/E 분리도 — bACC, thr, med_S/med_E

콘솔 첫 표(오피스 실측 432장). 답하는 질문: "이 지표는 S 와 E 를 가를 수 있는가?"

[INFO] S/E 분리도 (med_S 높고 med_E 낮을수록, bACC 1.0 에 가까울수록 좋은 지표):
  metric           med_S    med_E      thr   bACC  n(S/E)
  free_best       0.6637   0.7038   0.408  0.549  234/198   ← med_E > med_S (역전!)
  at_crosshair    (S 높음)  (E 낮음)  ...    0.52   229/71    ← E 는 crosshair 거의 없음
  mi_free         0.0749   0.0365   0.0477 0.627  234/198   ← 그나마 가장 높음
  ncc_free        0.0203  -0.0006   0.0145 0.598  234/198
  free_best_box   0.7007   0.7174   0.3602 0.61   210/161   ← box-crop 도 역전
  • med_S / med_E: S/E 그룹 점수의 중앙값. 좋은 지표면 med_S 높고 med_E 낮음.
  • thr (best_threshold): S/E 를 가장 잘 가르는 임계값. 모든 임계를 훑어 bACC 최대화하는 t 선택.
  • bACC (balanced accuracy): 이 진단의 핵심 한 줄. ↓

bACC — 왜 "그냥 정확도"가 아니라 "균형" 정확도인가

TPR (S 맞춘 비율) = (점수 >= thr 인 S) / (전체 S)     # 민감도
TNR (E 맞춘 비율) = (점수 <  thr 인 E) / (전체 E)     # 특이도
bACC = 0.5 * (TPR + TNR)                            # 코드: _separation

그냥 정확도는 클래스 불균형에 속는다. E 가 90%면 "전부 E"라고 찍어도 90% — 쓸모없는데 점수만 높다. bACC 는 S 정답률·E 정답률을 따로 평균하므로 한쪽만 잘 맞혀선 안 오른다.

bACC해석
1.0완벽 분리 (합성 self-test 값)
0.5동전 던지기. S/E 를 전혀 못 가름 (= 쓸모없음)
< 0.5역전. E 가 오히려 S 보다 점수 높음 (지표가 거꾸로)
실측 결론 free_best bACC = 0.549 — 거의 동전 던지기. 게다가 med_S(0.66) < med_E(0.70)로 방향이 살짝 역전(매칭 점수가 실패 이미지에서 더 높음)돼 있다. "matcher 변별력 부족"의 가장 강한 증거. MI(0.627)·box-crop(0.61)만 약하게 변별 → 단일 지표론 부족, 후보화+reranking 필요.

5gt-in-topK (proposer recall) — in_topk, rank1, miss

이 문서에서 제일 중요한 개념. 콘솔 셋째 블록(실측). 코드: _gt_in_topk.

[INFO] GT-IN-TOPK (S+crosshair, top-8 chamfer 후보의 proposer recall):
  in_topk=105/229 (0.459)  rank1=60 (0.262)  miss=124  median_miss_dist_norm=0.426
  rank_hist: {'1': 60, '2': 5, '3': 8, '4': 8, '5': 11, '6': 6, '7': 3, '8': 4}

왜 필요한가 — proposer vs reranker 갈림길

1단계 proposer(후보 생성기): 이미지를 훑어 "여기 같은데?" 후보 top-N 개를 뽑는다.
2단계 reranker(재정렬기):    그 후보들을 다시 채점해 1등을 고른다.
고칠 수 있는 문제 vs 못 고치는 문제
  • 정답이 후보 top-N 안에 있는데 순위만 밀림 (in_topk=True, rank>1) → reranker(MI)로 회복 가능.
  • 정답이 후보에 아예 없음 (in_topk=False = miss) → reranker 무의미. proposer 자체를 바꿔야 한다.

이 갈림길을 모르면 헛수고한다 — 후보에 정답이 없는데(proposer 문제) MI reranker 를 붙이는 건 시간 낭비. gt-in-topK 가 이 둘을 숫자로 가르는 계측이다.

용어뜻
in_topk정답이 chamfer 후보 top-N(기본 8) 안에 들어왔나. 거리 ≤ 0.20×짧은변
topk_rank정답이 몇 등으로 들어왔나. 1=chamfer 단독으로 1등, None=miss
rank1 / missrank==1 수 / 후보에 없는 수
in_topk_rate = proposer recall후보 생성기가 정답을 담는 비율 = 천장. 0.70 이면 reranker 완벽해도 최대 70%
rank1_ratechamfer 단독 정확도 (reranker 없이 지금 맞히는 비율)
rank_hist정답이 든 순위 히스토그램. 2·3등에 몰리면 reranker 여지 큼

읽는 법 (의사결정 규칙)

in_topk_rate 높음(0.9+) + rank1_rate 낮음  →  proposer 잘함, chamfer 순위만 나쁨
                                              ⇒ reranker(MI) 도입이 정답.
in_topk_rate 낮음(0.5)                      →  proposer 가 정답을 못 담음
                                              ⇒ reranker 무의미, proposer 교체.
실측 결론 (뼈아픔) in_topk_rate = 0.459. 정답이 후보 top-8 에 절반도 못 든다. MI reranker 를 완벽하게 만들어도 천장이 ~46%. rank_hist 상 든 것 중 60/105 는 이미 rank1, 나머지는 2~8 등에 얇게 퍼져(reranker 로 끌어올릴 여지 ~45건). 결론: proposer 자체가 약하다 → rcp 재등록·template 개선·proposer 교체가 reranker 보다 우선 (project_matcher_flat_chamfer_distinctiveness). reranker 는 그 위에 얹는 보조.

6참조 staleness(상대 기준) — rcp 가 낡았나?

또 다른 실패 원인: rcp(등록 reference)가 낡아 현재 공정 모습과 다름. 그러면 matcher 가 약한 게 아니라 기준이 틀린 것. 코드: _reference_quality.

아이디어 — 절대 점수는 함정, 상대로 본다 matcher 가 약하면 정답에서도 0.5 가 나오니 절대값은 못 믿는다. 그래서 상대 비교: 
1. recipe 의 S 이미지들로 "현재 대표 모습" = consensus(median 이미지)를 만든다.
2. s_internal = 각 S 가 consensus 에 맞는 정도 (S 끼리 얼마나 뭉치나)   ← MI 로 측정
3. rcp_vs     = rcp-center 가 consensus 에 맞는 정도
4. relative_ratio = rcp_vs / median(s_internal)

같은 metric(MI)으로 재므로 matcher 약함이 분자/분모에서 상쇄된다. S 끼리 뭉치는데(s_internal 높음) rcp 만 동떨어지면(rcp_vs 낮음) → ratio 낮음 → rcp 가 outlier = stale.

status뜻
stale_replaceS 끼리 뭉치는데 rcp 만 동떨어짐 → rcp 재등록 권장
S_inconsistentS 끼리도 안 뭉침(CV 큼) → consensus 불신, 판단 불가
low_texture_inconclusiveconsensus 정보량 낮음(저텍스처) → 판단 불가
insufficient_SS 장수 부족(<3) → 판단 불가
okrcp 가 S cluster 안에 있음

relative_ratio 낮을수록 stale 의심 · s_internal_cv(std/mean) 크면 S 끼리 안 뭉쳐 판단 불가. 임계는 cold-start(미보정) — golden 데이터셋으로 실측 calibration 예정.

7staleness ↔ recall 잇기 — crosstab · tertile · point-biserial

마지막 콘솔 블록. "staleness 가 정말 매칭 실패의 원인이냐, 아니면 무관한 혼동변수냐"를 가린다. §5(gt-in-topK)와 §6(staleness)을 교차시킨다.

[INFO] GT-IN-TOPK × 참조 staleness/ratio (원인 분리):
  status=stale_replace  n=...  in_topk_rate=...  median_ratio=...
  status=ok             n=...  in_topk_rate=...
  ratio tertiles:
    low   ratio=[..,..]  in_topk_rate=...   ← stale 후보 구간
    high  ratio=[..,..]  in_topk_rate=...   ← fresh 구간
  point_biserial(in_topk, ratio): n=... r=...  (+면 staleness 가 원인, ~0 이면 무관)
7.1 · 7.2 — status별 recall & ratio tertile

by_reference_status: 각 staleness status 그룹에서 recall(in_topk_rate)을 따로 본다. stale_replace 그룹 recall 이 ok보다 확연히 낮으면 → "stale 하면 매칭도 못 한다" 연결이 보임.

ratio tertile: relative_ratio(연속값)를 정렬해 low/mid/high 3등분하고 각 구간 recall 을 본다. low(stale)에서 낮고 high(fresh)에서 높으면 → 단조 관계 = staleness 가 원인이라는 패턴.

왜 tertile 로 자르나: status 라벨(이산)은 임계에 민감. 연속값을 구간으로 직접 보면 임계와 무관하게 "ratio↑일수록 recall↑"의 추세를 본다.

7.3 point-biserial correlation — 추세를 숫자 하나로

  • point-biserial r = "한쪽 이진(binary), 다른 쪽 연속(continuous)"인 두 변수의 상관계수. 여기선 in_topk(1/0) 와 relative_ratio(연속)의 상관.
  • 사실 Pearson 상관계수와 수식이 똑같다 — 한 변수가 0/1 일 때 Pearson r 을 부르는 이름일 뿐. 코드도 Pearson 공식:
r = cov(x, y) / (std(x) * std(y))     # x=ratio(연속), y=in_topk(0/1)
r (−1 ~ +1)해석
+ (예 +0.42)ratio↑일수록 in_topk↑ → staleness 가 recall 저하의 원인 (rcp 재등록이 약)
≈ 0무관 → staleness 는 혼동변수, 원인은 다른 데(matcher 변별력)
−역방향 (이론상 이상, 데이터 의심)
왜 결정적이냐 §5 에서 recall 이 낮다고 나와도, "rcp 가 낡아서"인지 "matcher 가 약해서"인지 모른다. point-biserial 이 0 에 가까우면 → staleness 핑계를 배제하고 "원인은 matcher 자체"라고 못박을 수 있다. = 혼동변수 제거용 한 줄 통계.
주의 상관 ≠ 인과. r 이 커도 "stale → low recall" 인과를 증명하진 않는다(둘 다 저텍스처 recipe 라 같이 움직였을 수도). 그래서 tertile·status·biserial 을 함께 보고 종합 판단한다. 실측에선 scored=71 중 stale=17·ok=4·판단불가=50 으로 표본이 적어, tertile/biserial 은 golden 데이터셋 후 재측정 예정.
