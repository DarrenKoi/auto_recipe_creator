2제안 1 · 극성 정합 (OM-D)

2.1 무엇이 깨지는가 — 계산으로 증명된다

OM-D 는 OM 의 명암이 반전된 화면이다. 반전은 두 채널에 정반대로 작용한다.

  • chamfer 채널(C1/C2/C3) 은 Canny edge → distance transform 위에서 돈다. edge 는 gradient 크기라 반전에 불변이다. 즉 proposer 는 정상 동작하고 후보 좌표는 여전히 옳다.
  • NCC rerank 는 부호에 민감하다. 반전된 진짜 정답의 NCC 는 ≈ −1 이고, 코드는 ncc_pos = max(0.0, ncc) (engine.py:967) 로 음수를 0 으로 눌러 버린다.
완벽하게 맞는 key 라도, 반전 상태에서는 sel = 0.5 · chamfer + 0.5 · 0 = 0.5 · chamfer ≤ 0.5 chamfer = 1.0 인 이상적인 경우에도 상한이 0.5 — match 임계 0.6053 을 구조적으로 넘을 수 없다

결과적으로 adjust 대역(0.4727 ≤ sel ≤ 0.5)에 갇히고, 게이트는

  • distinctive 가 없으면 → engineer_review (correction.py:214)
  • 있으면 → act 로 가지만, 좌표를 chamfer 절반의 정보로만 고른 것이다

오피스 OM 실측이 score ≈ 0.533 이었다는 사실과 이 상한(0.5)이 수상하리만치 가깝다. OM-D 화면에서 찍힌 프레임이 섞여 있었다면 설명이 된다 — 지금은 확인할 방법이 없다.

2.2 더 중요한 것 · 극성 불일치는 align fail 의 원인일 수 있다

recipe 가 OM-D 로 등록됐는데 화면이 OM 이면(또는 반대), 장비 자신의 align 루틴도 같은 반전 영상을 본다. 즉 이것은 "우리 matcher 가 불리해지는 조건" 이 아니라 align fail 자체의 한 실패 계급일 수 있다. 그렇다면 올바른 조치는 점수를 우회하는 것이 아니라 화면 모드를 recipe 에 맞추는 것이고, 그것이 곧 보정이다.

2.4 제안

(a) 화면 모드를 읽는다 — 새 센서. 오늘 만든 monitor/manual_image_mode_change.py 의 read_mode() 가 그 센서다. Image 콤보의 화살표 왼쪽을 OCR 로 읽어 OM | OM-D | SEM 을 단어 전체로 확정한다 (부분 일치 금지 — om 은 om-d 의 접두다). 이 함수를 cycle.py 가 사전 조건 판독으로 재사용한다.

(b) recipe 의 등록 극성을 안다. 둘 중 오피스에서 확인되는 쪽:

  1. cond.txt 에 모드/극성 필드가 있는지 확인 오피스 확인 필요 — 있으면 이것이 정본
  2. 없으면 등록 이미지의 밝기 분포로 추정. 단 추정이므로 판정이 아니라 경고로만 쓰고, 실제 판별은 (c) 로 한다

(c) 극성 probe — 판별의 정공법

chamfer best 후보 자리에서 NCC 의 부호를 본다. 지금 코드는 max(0, ncc) 로 이 정보를 버리고 있다.

ncc(best) ≈ +높음   →  극성 일치
ncc(best) ≈ −높음   →  극성 반전  (|ncc| 가 큰 것은 오히려 '잘 맞는다' 는 증거)
|ncc| 낮음          →  자리가 틀렸다 (극성 문제 아님)

이 세 갈래는 추가 계산이 한 번도 필요 없다 — 이미 계산한 ncc 의 부호를 버리지만 않으면 된다.

(d) 조치는 화면 쪽으로. probe 가 반전을 말하면 change_image_mode 와 같은 경로로 화면 모드를 recipe 쪽으로 바꾸고 다시 캡처한다. 바꿀 수 없으면(콤보 미검출/항목 미확인) 보정하지 않고 cube — 추측해서 누르지 않는다.

(e) 안전망 · 극성 불변 매칭은 폴백으로만. abs(ncc) 1줄 수정은 유혹적이지만 기본 경로로 삼지 않는다.

  • 임계 0.6053/0.4727 은 max(0,ncc) 분포에 묶여 있다 (engine.py:158 경고). 부호를 풀면 배경 후보의 sel 도 같이 올라가 오탐이 늘고, 재캘리브레이션 없이는 두 임계가 무의미해진다
  • workflow_2 lab 과의 bit-parity 가 깨진다

따라서 극성 불변은 ALIGN_FAIL_POLARITY_INVARIANT=1 킬스위치 뒤 진단용으로만 두고, 운영 기본은 (d) 의 화면 정합이다.

2.5 작업 목록

  1. read_mode 를 공용으로 옮기고 cycle 의 사전 판독에 배선
  2. AlignKeyMatchResult 에 best_ncc(부호 유지) 추가 — 기록만, 판정 불변
  3. route_template 키 3-state 확장(OM-D → OM template + inverted=True)
  4. 보정 진입 전 screen_mode != recipe_mode 면 모드 변경 1회 → 재캡처
  5. 실패 시 새 status image_mode_mismatch(cube 로 나가고 corrected 아님)

  • OM-D 화면 paused 프레임의 score, chamfer, (작업 2 후) best_ncc 부호
  • 같은 recipe 를 OM 과 OM-D 에서 각각 한 장 — 이 한 쌍이 2.1 의 상한 0.5 를 실측으로 확정한다

3제안 2 · SEM search-around 는 frac 목표 zoom-out 이 전제다

3.1 OM 에서 통한 것이 SEM 에서 통하지 않는 이유

stride = max(0.1 · frame, (frame − template) · 0.9)
key 가 차지하는 비율footprintstride예산 10 의 도달 반경
OM10~20%≈ 0.8~0.9 FOV≈ 0.75 FOV격자가 성립 오피스 성공
SEM80~100%≈ 0하한 0.1 FOV±0.2 FOV — 사실상 제자리

셀 수를 늘려 풀 문제가 아니다 — 반경은 예산의 제곱근으로만 자란다. zoom-out 으로 frac 을 내리는 것이 유일한 레버다.

3.2 제안 · zoom-out 목표를 min_key_px 가 아니라 목표 frac 으로

현재 choose_zoom_out_mag(…, config.min_key_px) 는 key 가 너무 작아지지 않게만 본다(하한). 필요한 것은 상한이다 — key 가 프레임의 몇 %를 차지해야 격자가 성립하는가.

stride = FOV · (1 − frac) · 0.9
n² ≥ (2R / stride)² target_mag ≈ reg_mag · (frac* / frac_now)

권고 frac* = 0.30 (stride ≈ 0.63 FOV). 예산 10 이면 3×3 격자로 ±1 FOV 를 덮는다. min_key_px 하한과 frac* 상한을 둘 다 만족하는 단을 고르고, 충돌하면 degrade 로 빠지되 이유를 남긴다(reason="no_mag_step_for_frac") — 지금처럼 조용히 좁은 격자를 도는 것보다 낫다.

3.3 SEM 고유 주의점

  • 휠 금지, PM 절대 단만. OM 은 휠로 등록 단을 맞추지만 SEM 배율에서 휠 한 칸은 FOV 를 크게 흔든다
  • ECC rerank 는 SEM 단독 순위다. ECC 도 상관 기반이라 극성에 민감하지만 SEM 에는 dark 모드가 없다 확인됨 09-22 — 극성 반전은 OM ↔ OM-D 사이에서만 일어나므로 제안 1 은 SEM 경로에 해당하지 않는다. SEM 은 제안 2(frac) 만 필요하다
  • aperture problem: SEM key 는 junction 이 유일점이고 주변 line/flat 이 점수를 희석한다. zoom-out 하면 junction 이 픽셀 몇 개로 줄어 악화된다 — frac* 를 0.1 처럼 과하게 낮추면 안 되고 0.25~0.35 가 타협점

5제안 4 · 재등록 루프를 닫는다

측정된 사실: SEM 은 rank-1 ≈ 0.5(동전 던지기)이고, template-bank / RRF / ensemble 3종이 같은 벽에서 멈췄다 (2026-06-25 결론: member-fusion 으로는 넘을 수 없다). 남은 레버는 matcher 가 아니라 어떤 자리를 key 로 등록했는가다.

지금도 feasibility_check 가 reregister_recommended 를 내고 cycle 이 notes·감사 로그에 남긴다. 없는 것은 그 신호가 사람에게 도달하는 경로다.

제안: Episode 수집(ALIGN_FAIL_EPISODE_COLLECT=1)을 켜서 알람마다 second_ratio/decision/outcome 을 쌓고, 주 1회 worklist 를 엔지니어에게 넘긴다. 코드 작업은 거의 없고 운영 절차가 본체다.

6제안 5 · consensus 의 조용한 rcp 폴백을 막는다

열린 의심: a33f8c4 이후 consensus 가 rcp 와 크기/배율이 다른 S 이미지를 버리는데, 그 결과 pool 이 min_s(3) 미만이 되면 경고 없이 rcp 로 떨어진다. 오피스에서 본 match → adjust 강등의 후보 원인이다.

  1. 드롭 사유를 세어 한 줄로 — [INFO] consensus[OM] n=8 → kept=2 (size_mismatch=5, mag=1)
  2. kept < min_s 폴백은 [WARNING] 으로 승격(지금은 조용하다)
  3. verify_consensus_path.py 오피스 1회 실행 — 경로 keying(eqp 무관) 확인

consensus 는 rcp 를 전제로 한다(crop 크기를 등록 key 에서 가져온다). rcp 가 0장이면 consensus 도 0장이고 경고조차 없으므로, no_assets 진단에서는 항상 rcp 부터 본다.

7제안 6 · Verification 을 stub 에서 올린다

지금 corrected 는 자기보고다. reposition 잔차가 tol 안에 들어왔고 OK 를 눌렀다는 뜻이지, 측정이 실제로 진행됐다는 증거가 아니다.

제안: Assist 패널의 분자(측정 카운터) 판독을 오피스 캘리브레이션으로 확정하고 primary Verification 3-상태를 채운다. 그러면

  • corrected 인데 측정이 안 도는 경우를 잡는다 (지금은 영원히 모른다)
  • Outcome 파생이 fallback(분자 per-read) 대신 primary 를 쓴다

이것이 완성되기 전까지 "보정 성공률" 이라는 숫자는 우리가 누른 횟수일 뿐이다.
